## 1. What runs, and which port serves `POST /v1/query`

Read from `AwsRuntime.scala` and `AwsSettings.scala` (re-read after WO-8b): role `both` starts the fast server on 8080 (evidence, graph, explain, ops) and the slow server on 8081 (`POST /v1/query`, jobs, ops) in one process. `GET /healthz` answers on each port with no dependency call. Query records, jobs and idempotency are in-process, so `/v1/evidence` and `/v1/explain` work only in the task that served the query: Phase 15 therefore runs ONE service, `query` (`service_layout = "combined"`, command `scholarchain.services.runtime.AwsRuntime both`), not two.

- ALB listener: HTTP 80 (an internal ALB DNS name has no certificate; the bearer token crosses the VPC unencrypted, accepted risk for the human to confirm). Target group: HTTP 8081, target type `ip`, health check `GET /healthz` on the traffic port, 200, interval 15 s, timeout 5 s, healthy 2, unhealthy 3, deregistration delay 30 s. Port 8080 is not reachable through the ALB.
- Chain of security groups: load-client SG -> ALB SG (80) -> services SG (8081). The ALB SG has exactly one ingress rule (from the load-client SG); the services SG gets one new ingress rule (from the ALB SG, 8081). No CIDR rule, no public subnet, no public IP; the ALB is `internal = true` in the two private app subnets.

### Health-check grace period (WO-8b fact: no port listens until the export is loaded)
`health_check_grace_seconds = 300`. Reasoning: image pull from ECR through the interface endpoints (tens of seconds), JVM start (seconds), S3 download of at most 128 MiB (`ExportLimits.Default`) over the gateway endpoint (seconds), checksum verification and parse of at most 128 MiB of JSON on 0.5 vCPU (UNVERIFIED, assumed 20 to 60 s), plus the Neptune and Titan clients (lazy). Estimated 1 to 2 minutes; 300 s leaves 2.5x margin. After the grace period three failed checks at 15 s (45 s) mark the task unhealthy. PROVISIONAL: the local measurement (section 7) gives the real start time. A scale-out task therefore serves traffic 1 to 3 minutes after the scaling action.

## 2. Task memory and CPU (PROVISIONAL)

Task sizes, Fargate X86_64: query 512 CPU / 4096 MiB; worker 512 CPU / 1024 MiB; load client 1024 CPU / 2048 MiB; loader unchanged (2048 / 8192 in the S overlay).

Query memory arithmetic. The export is held whole in the heap (WO-7b, WO-8b). `ExportLimits.Default` bounds it at 128 MiB of files and 1,000,000 rows. Parsed JSON costs several times the file size: take 6x, so 128 MiB x 6 = 768 MiB, plus one object parsed at a time (at most 128 MiB) = about 900 MiB of live heap at the bound. Headroom 2x for GC copying and request load: 1.8 GiB heap. Heap is 75 percent of the container (`MaxRAMPercentage=75`), so the container needs 1.8 / 0.75 = 2.4 GiB, plus about 0.3 GiB non-heap (metaspace, threads, SDK buffers) = 2.7 GiB. The next Fargate size at or above it is 4096 MiB (about 3 GiB heap), which is also service-engineer's recommendation. 4096 MiB is the largest pair that 512 CPU allows, so 0.5 vCPU stays. The 324 MB figure of the S overlay comment and the local rehearsal export (P15-25) is the old 11-table export, ABOVE the 128 MiB limit. It is superseded: check 2.10 PASSED for A's 17-table export, nine loaded tables plus the root at 100.9 MiB in 34 objects, within the limit (`docs/agent-runs/phase-15/session-ab/session-record.md`). The final memory follows the ratified P15-30 rule of section 7, not the arithmetic of this section: the 4096 MiB here is the provisional value until the heap measure.

Trade-off, CPU against memory. service-engineer recommends at least 1 vCPU for role `both`; the human requires CPU small enough that D's load scales the service out. 512 CPU keeps both: the primary scale-out trigger is request count per target (independent of CPU), and a smaller CPU only makes the second (CPU) policy more likely to fire and the export parse slower at start (covered by the grace period). Cost of 1 vCPU instead: +0.0202 USD an hour per task. The variables `service_cpu`, `service_memory` and `service_jvm_options` (JAVA_TOOL_OPTIONS, empty by default) change all three without a code edit.

Worker: one message in flight, text at most 50,000 bytes, four SDK clients: 1024 MiB is a sizing guess (UNVERIFIED; no measurement).

## 3. Scaling

### Query service (graph-retriever row)
Target tracking, two policies on one target, `min 1`, `max 4` (4 x 0.5 = 2 vCPU of the 30 vCPU Fargate quota; the worker adds at most 2, the load client 1, the 2 vCPU loader runs in an earlier apply: 5 vCPU in the worst case).
- `ALBRequestCountPerTarget` target 300 requests per target per minute (5 per second).
- `ECSServiceAverageCPUUtilization` target 60 percent.
- Scale-out cooldown 60 s, scale-in cooldown 300 s. Scale out when either metric exceeds its target; scale in only when both are below (documented Application Auto Scaling behavior, UNVERIFIED here).

D arithmetic (from `load-tests/query-load/README.md`): a closed-loop client cycles in latency L plus a think time uniform 2 to 4 s (mean 3.0 s), so the rate is clients / (L + 3.0). On one task: 8 clients, L = 0.5 s: 2.3 per second = 137 per minute (below 300, no scale-out). 24 clients: 24 / 3.5 = 6.9 per second = 411 per minute, and even at L = 2 s 4.8 per second = 288 per minute (about at the target). 48 clients: 48 / 3.5 = 13.7 per second = 823 per minute (2.7x the target, the "about 14 per second" of WO-11); at L = 0 it is 960 and at L = 2 s 576 per minute (1.9x). The target is therefore crossed at the 24 level and clearly at the 48 level; the policy computes about 3 tasks at 48 clients (823 / 300 = 2.7), under the max of 4. Expected shape: 1 task, then 2, then 3 across the 24 and 48 levels.

CPU capacity estimate (UNVERIFIED, no measurement): at 20 ms of CPU per request, 14 requests per second use 0.28 vCPU, 56 percent of a 0.5 vCPU task, so the CPU policy can fire too but is not relied on. Per-task capacity is bounded by the code: 8 HTTP threads and a call pool of 16 with a queue of 32 (`ServiceConfig` defaults), so one task can hold 48 concurrent requests (16 + 32) with no spare: the first minutes of the 48-client level on one task can show 429/503 rejections before the new tasks serve traffic. That is a measured finding for D, not a defect to tune during the run.

Scale-in: with no client for 15 minutes the metrics are 0. Target tracking scale-in uses a 15 one-minute-datapoint alarm (documented behavior from memory, UNVERIFIED), so the first scale-in action comes about 15 to 17 minutes after the last request, at or just after the end of D's zero period, plus about one minute for ECS to stop the tasks. The human therefore keeps the services up at least 25 minutes after the client ends and confirms the desired count is back at 1 before moving to E (section 6 command). Whether `ALBRequestCountPerTarget` with no traffic counts as zero for the scale-in vote is UNVERIFIED; the CPU policy has data at idle, which is why both policies exist. A p95 alarm (`TargetResponseTime` p95 at or above 2 s for 3 one-minute periods) signals only.

### Embedding worker (embedding-worker row)
Step scaling on backlog per task = visible messages / running tasks (`AWS/SQS` `ApproximateNumberOfMessagesVisible` over `ECS/ContainerInsights` `RunningTaskCount`, metric math `FILL(m1, 0) / IF(FILL(m2, 1) > 0, FILL(m2, 1), 1)`, one-minute periods; the expression is UNVERIFIED and the alarm state must be checked after apply, section 6). `min 1`, `max 4`.
- Out alarm: backlog per task at or above 150, 1 of 1 datapoints. Steps: 150 to 450 add 1; 450 and above add 2. Cooldown 60 s.
- In alarm: backlog per task below 20 for 5 of 5 datapoints. Steps: 5 to 20 remove 1; below 5 remove 2. Cooldown 180 s.
Arithmetic: one task handles one message at a time, about 2 to 3 messages per second (UNVERIFIED; WO-7 says one message in flight, S run 6 embedded 9 vectors per second serially in the loader). C enqueues 2,000: backlog per task 2000 at 1 task, so the first alarm adds 2 (3 tasks, 667 per task), the next adds 2 (4, the max). At 2.5 per second per task, 4 tasks drain in about 2,000 / 10 = 200 s after they run; the first reaction comes about 1 to 2 minutes after the enqueue plus about 1 minute for a task to start, so the drain shows scale-out and a falling backlog. 4 tasks x 2.5 = 10 messages per second stays under the Titan V2 limit (300,000 tokens per minute is about 16 messages per second at 300 tokens, `COST_ESTIMATE.md` D2a): a higher max would throttle and throttled messages count toward `maxReceiveCount` 3. The queue's `maxReceiveCount` is unchanged at 3. Worker env `SCHOLARCHAIN_WORKER_VISIBILITY_SECONDS=60` and `_LEASE_SECONDS=50` (code ranges 30 to 900 and 10 to visibility - 5; code defaults 120 and 100) so a poison message reaches its third receive in about 3 to 4 minutes (F); the queue's own visibility timeout stays 300 s.
Scale-in after drain: 5 minutes of low backlog, then -2 (4 to 2), 180 s cooldown, then -1 or -2 (to 1): about 8 to 10 minutes after the drain. C's collection must continue until `RunningTaskCount` is back at 1 (section 6 command).
