## Required behavior (course jobs 1 to 11)
Implement in `modules/spark/**`, with module tests under `modules/spark/src/test/scala`. Each item needs a named test that proves it (see Tests).

1. **Canonical builder.** Build Researcher, Work, AUTHORED, Topic, Institution, Venue tables. Researcher node ID is `canonicalResearcherId` when non-null; an unresolved mention is its own node with `nodeKind = unresolved-mention` and its mention ID as identity, never merged. Works map through `canonicalWorkId`, and duplicates (merged work clusters) are counted ONCE per canonical work in every publication count, pair weight and team size. Every AUTHORED edge must point to existing nodes; violations go to an `integrity-violations` table with a reason and counts (not dropped silently, not fatal unless a configured ceiling is exceeded). A table of unresolved mentions with the reason (`unlinked` or `integrity-failure`) is exported.
2. **Temporal weighted coauthorship graph.** Map Hadoop pair candidates to node IDs through the mention links; drop self-pairs (two mentions of one canonical researcher in one work); canonical undirected pair order (use the core pair canonicalization rule); aggregate duplicates by distinct canonical work. Store `jointPublicationCount`, `firstCollaborationYear`, `lastCollaborationYear`, representative work IDs (bounded, deterministic choice documented) or a stable pointer, and the window. Windows are configurable (default documented, e.g. 2000 to 2005 and so on, plus an all-years window) and are explicit in every output row. Works with no year are excluded from windowed outputs and counted (state it).
3. **Breadth and team-size statistics** per researcher and window: `P_r, C_r, T_r, A_r, M_r, W_r` and the work IDs responsible for `M_r` (all ties kept), each as its own column. State precisely how unresolved coauthor mentions enter `C_r` and `T_r` (recommended: `C_r` counts distinct coauthor NODES; add visible columns for the number of unresolved coauthor occurrences so the inflation by unlinked mentions is measurable) and document it as a limitation. Team size for a work = number of authors of the canonical work, counted once.
4. **Connected components** (distributed, e.g. iterative min-label propagation with checkpointing or a star-contraction method): component ID, size, fraction of nodes in the largest component, singleton count, per window.
5. **Paths.** Bounded multi-source BFS by DataFrame joins from selected pairs given by a config file or argument (no all-pairs, no driver collection of the graph); hop limit explicit; deterministic shortest path with per-hop edge and supporting work IDs, materialized into `path-evidence`; a pair that is unreachable within the bound is recorded as such. Sampled estimate of component-level average path length and effective diameter (fixed seed, documented sample size and limitation).
6. **Communities.** Documented method (for example deterministic label propagation with fixed iteration cap and min-label tie-break, which must also be shown to terminate or stop at the cap with that fact recorded). Store membership, community size, cross-community edges, per window.
7. **Bridge measure.** At least cross-community degree and number of distinct communities connected, plus participation coefficient (define each formula in the module doc and in the output schema notes; state limitations: community-method dependence, no exact betweenness here). Record algorithm parameters.
8. **Coreness.** Distributed k-core by iterative peeling; document termination and checkpointing; test on small hand-checkable graphs (triangle with a pendant, clique, path).
9. **Temporal analysis.** For consecutive windows: change in distinct coauthors, team sizes, component membership (overlap-based, since component IDs are window-local), community membership, and bridge values, with an explicit statement of the inclusion rules and where windows are not comparable (a researcher absent from a window, years missing, changing graph).
10. **Semantic summaries.** Researcher-profile, community, collaboration-path and selected paper or topic summaries generated by template from computed columns and source records only; each summary row lists the evidence it used (work IDs, metric names, window) and cites provenance. No LLM, no network, no invented numbers.
11. **Export.** Partitioned Parquet under `/Users/winnguyen/scholarchain-data/phase6-out/spark/run=<run id>/` for nodes, edges, metrics, components, communities, bridge, coreness (columns may live in the metrics table if separate tables are also exported), path-evidence, temporal comparison, semantic summaries, unresolved mentions and integrity violations. Partition by window where it helps. Local load manifests (JSON) for Neptune, DynamoDB, S3 Vectors and ordinary S3: for each, the planned tables and prefixes, row counts, schema, and SHA-256 per file. Nothing is uploaded and no bucket name or AWS identifier appears.

## Operational requirements (verbatim intent of the course)
- Real distributed transformations on `Dataset[Row]`; never collect the full graph (or any table that scales with the graph) to the driver. Route every `collect`/`toLocalIterator`/`take` through ONE guarded helper with an explicit row cap and a test proving it throws above the cap. Allowed driver-side data: small configuration, selected path pairs, aggregate counts, and bounded samples.
- Explain partitioning and shuffle boundaries (partition keys, `repartition`/`shuffle.partitions`, joins and skew handling, broadcast choices). Persist, in the run output, the physical plans (`explain`) for each major stage and the observed stage metrics (partition counts, shuffle read and write bytes, task counts) captured via a SparkListener or status tracker. Document the stage DAG in a design note inside the module (`modules/spark/DESIGN.md`).
- Configure checkpointing for iterative algorithms (components, communities, coreness, BFS) with a checkpoint directory under the run output; lineage must not grow unboundedly.
- Emit counts and invariant failures (nodes, edges, per-window sizes, component, community and coreness distributions, integrity violations, dropped self-pairs, works with no year).
- Reproducibility: a run manifest written with the output (inputs and their digests, ER run ID and Hadoop run ID, snapshot, config and window definitions, algorithm parameters and seeds, counts, Spark/Scala/Java versions, git head, sources digest). Deterministic IDs, ordering and tie-breaks; the same inputs give the same logical output (tested).
- Provenance on every output row (source, snapshot, transform version, run ID), using the core `Provenance`.
- Entry point: `scholarchain.spark.CollaborationPipeline` (or your name), arguments for ER run directory, Hadoop run root, output root, windows, path pairs file, sample size, master and partitions, with strict argument parsing and a refusal to write inside the repository or `target/`.
