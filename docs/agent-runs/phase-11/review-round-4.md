# Phase 11 review, round 4 (fresh code-reviewer, Opus, read-only): REQUEST_CHANGES on repair round 3 (as received, condensed)

Scope: Phase10Http.scala, Phase10RepairSuite.scala, Phase10ApiContractSuite.scala, new Phase10EarlyCloseSuite.scala. Read, Grep, Glob only; no commands. Findings are recorded for the human and not repaired unless the human directs it.

Summary: no wrong behavior passes in practice, but three gaps. The "server never processed the body" requirement is still only indirect, the replay path checks less than the normal path, and the 413 fallback does not match server behavior.

- **F1 (Medium, test-engineer; service-engineer only if an observer is wanted).** Phase10Http.scala:617-625. The service never logs the request question (Http.scala:361-379 logs only key presence and exception type), so "marker absent from logs" proves almost nothing. A handler that reads the body after the 401 would still pass; the replay closes its own socket and healthz stays green. Stronger proof with no services change: send the 5 MiB on a raw socket, writer thread in chunks, main thread reading; assert the `HTTP/1.1 401` line arrives while bytes written are well below the declared length (writer IOException tolerated only after the 401 is read). Optional: with `metrics.enabled`, assert the /v1/query counter rose by exactly one 401 (Http.scala:394). Caveat: the JDK HttpServer may drain up to 64 KiB of an unread body on close.
- **F2 (Medium, test-engineer).** Phase10Http.scala:609-614. The replay checks only status line, top-level `error` key and code; content type, X-Request-Id/X-Trace-Id, message, traceId/requestId, details and leak checks are skipped. Fix: build a `Resp` from the parsed status, headers and body in `rawHeadAnswer` and call `assertTypedError`.
- **F3 (Low-Medium, test-engineer).** Http.scala:221, 286-287: an authorized body at or under `oversizeDrain` (4 MiB) is read to the end and discarded before the 413. The 3 MiB case (Phase10ApiContractSuite.scala:205-213) is read by design, so it should not race. If the fallback fired, the replay would declare about 3 MiB, send 2048 bytes and fail after 5 s with a misleading "hangs" message (fails closed). The helper doc comment at Phase10Http.scala:571 ("refuse before reading") is false for 413, and the report-10 claim that the 413 case "had the same race" is unsupported by the code. Fix: document the drain, or keep the fallback for head-time refusals (401/403) only.
- **F4 (Low, test-engineer).** Phase10Http.scala:497-499. `isEarlyClose` substrings "eof" and "closed" also match a server that reads the whole body then drops the connection (JDK: "header parser received no bytes", EOFException). Require broken pipe, connection reset or "fixed content-length"; drop bare "eof" and "closed".
- **F5 (Low, test-engineer).** `rawHeadAnswer`: only SocketTimeoutException is caught (:565-567), so a reset escapes as a raw error (fails closed, unclear). Chunked: only the first chunk is read; a chunk extension breaks parseInt; any Transfer-Encoding counts as chunked. Content-Length counts bytes but the reader counts UTF-8 chars (non-ASCII bodies wait for the timeout). Correct: length framing, 5 s timeouts, close in finally.
- **F6 (Low, test-engineer).** Phase10EarlyCloseSuite: the fake server resets without a response, so it does not reproduce "401 sent, then fixed content-length ... Broken pipe" (covered only by a synthetic exception, :105-111); the refused-connection test does not assert ConnectException (:59-74); the timeout test's `HttpClient.newHttpClient()` is never closed (:79); no test of the replay guard (early close then 200, 5xx or hang); the current `rawHeadAnswer` has never run end to end because the race did not fire.
