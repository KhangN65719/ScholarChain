## Findings (all ACCEPTABLE-OPEN)
- F1 (infra-engineer; fix before the first M pipeline run). modules/workflow/main.tf sets `TimeoutSeconds = var.step_timeout_seconds` on CreateCluster (line 35) and RunLoader (line 118) as well as the Hadoop and Spark steps; a failure in either goes to `Failed`, not `CleanupOnFailure`. COST_ESTIMATE.md:176 assumes loader times S 0.5 to 1.0 h, M 1.0 to 2.0 h, L 2.0 to 4.0 h, but the overlays set S 1800 s, M 2700 s, L 3600 s (experiment-size-{s,m,l}.tfvars lines 20, 21, 23). On the estimate's own assumptions RunLoader times out on M and L at both bounds and on S at HIGH. Before round 2 the uniform 3600 s already failed L and M at HIGH; round 2 makes M fail at LOW and S at HIGH too. Each failure costs a re-run and a new approval record. infra/terraform/README.md:138 says a CreateCluster hang "ends in the execution timeout"; CreateCluster has its own step timeout, the hang ends there and goes to `Failed`; cleanup is still skipped. The stated rule holds only just: cluster start is capped at one step timeout, so S worst case is 3 x 1800 = 5400 s, equal to the run timeout; on M a start between 1800 and 2700 s breaks the rule. Fix: a separate loader timeout, or reconcile loader hours with the step and run timeouts. Matters only once Phase 14 runs.
- F2 (test-engineer). The new N2 control uses `graceMillis = 1000` (Phase10EarlyCloseSuite.scala:597) while the baseline (Phase10Http.scala:595) and the real-service checks (Phase10RepairSuite.scala:308, 318) use the default 500 ms. With a 200 ms delay and a fast loopback read it would very likely also fail at 500 ms, but it should use the grace period it claims to prove. Otherwise the N2 repair is verified: the calibration fake reads only the request head then sleeps (`finally` closes its socket); the at-answer assertion runs first and the control checks the message names the after-grace check; limits only got tighter (after-grace about 4.5 MiB to 2.75 MiB); no existing test weakened. Real-service margins about 1.19 MiB (at-answer) and 1.75 MiB (after-grace) under the limits: reasonable on macOS (same OS buffers), one sample, Linux unverified.
- F3 (infra-engineer). COST_ESTIMATE.md:79 and :235 assume Neptune is up for only 1 to 2 h of the 4 to 6 h run 14.0, "applied by itself and not through an overlay"; no file or documented flow does this. If 14.0 uses the S overlay, the estimate's own whole-session rule adds about $0.18 LOW and $0.40 HIGH, putting S+M HIGH at about $25.82. Labelled an assumption.
