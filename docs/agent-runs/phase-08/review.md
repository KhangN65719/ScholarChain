### Blocking
**B1 (storage-engineer, Medium-High). Same-`executionLabel` rerun skips batches by position, not by content.**
- `EmbeddingWork.scala:160-170`: a batch's ledger record is keyed only by `STAGE#batch#<index>#<ordinal>`. Neither the run record nor the batch records store the manifest SHA or the batch's items; `begin` (`:144-155`) never compares the new manifest with the old one.
- `EmbeddingIngest.scala:345-346`: `if prior.exists(_._1 == "FINISHED") then t(2) += items.size` skips a batch without opening it.
- Result: with changed input under the same label (text, model, template, added or removed rows), every already-FINISHED position counts as "resumed". Changed text is not reported; new keys landing in a finished position are never embedded or written yet count as skipped. Nothing is overwritten, so the letter of the gate holds, but it is silent and new rows are lost without notice.
- `IngestMain` hides it (fresh in-memory bucket and ledger each run; its `accounted` check `IngestMain.scala:266-269` catches a missing vector only for that reason). A persistent ledger (Phase 12 DynamoDB) would hit it.
- Fix: store the manifest SHA on the run record and a digest of each batch's items on its batch record; on resume refuse with a distinct error code if either differs, or require a new label.
- Tests: test-engineer turns `Phase8IngestSuite.scala:666` (`.fail`) into a plain test in the same repair round (it turns red once B1 is fixed); add same-label cases for an added row and a changed model.
