## Error naming and a bounded tolerance (work orders 112 and 113; commit c4ebc1f)
- Storage: the loader fetches the Neptune error records (paged, de-duplicated by file, record and code, cap 500 per job) for any job that is not a clean success and prints `NEPTUNE_LOAD_ERROR` and `NEPTUNE_LOAD_ERRORS_TOTAL` lines; `failOnError` is now an option (default true); edge jobs run at `parallelism LOW`; every start request sends `mode NEW` (the AWS default `AUTO` resumes a previous load of the same source); `BulkLoadResult` exposes totals, named records and per-job statuses. With `failOnError=false` a job ending `LOAD_COMPLETED`, or `LOAD_FAILED` with error counters above zero, is returned instead of thrown (the second form is a hedge: the AWS pages do not say which status a skipped-records load ends with; UNVERIFIED, see below).
- Rag: `--tolerate-load-errors` with an explicit policy (human decision): 0 errors is `LOADED`, `LOADER_RESULT=SUCCESS`; errors at most 0.1% of Neptune's `totalRecords` AND every error named AND only record-level codes is `LOADED_WITH_ERRORS` with `LOADER_RESULT=SUCCEEDED_WITH_WARNINGS` (exit 0) and a report that says "This is NOT a clean load"; otherwise FAILED. Never tolerated: `OUT_OF_MEMORY_ERROR`, `S3_ACCESS_DENIED_ERROR`, `FILE_MODIFICATION_OR_DELETION_ERROR`, unknown codes. `INTERNAL_ERROR` is tolerated and disclosed as unclassified. A tolerated `LOAD_FAILED` job is reported with "it is UNVERIFIED whether the rest of each file was loaded" and `loadCompletenessVerified: false`. Neptune's `totalRecords` counts property-level records, not CSV lines, and is never compared with CSV row counts.
- Reviews: independent review of work orders 112 and 113 REQUEST CHANGES (B1 the unverified status string; I1 job-level codes tolerated; A1 page de-duplication; mode `NEW`); one batched repair round; a narrow re-review REQUEST CHANGES with one wording finding (I-R1: a tolerated `LOAD_FAILED` job must not claim the named records were skipped); repaired with a wording change pinned by tests and one agent `sbt check` (exit 0, `[success]`, Failed 0, Errors 0; the rag load-error suite reported 40 tests in its XML report). The group totals the agents printed (93 and 1,133) are identical to the human's clean check of 02437a9 and probably do not include the module suites that grew since; the human's `sbt clean check` at the phase gate settles the counts. Per the human's limit of one review round, no further review of that one-sentence change was run.
- Harness: 12 further cases for `--tolerate-load-errors`, `pass=1453 fail=0`.
- Deployed as package-9, plan-14 (image tag only), deploy-14, task definition revision 15.

## S run 10 (HEAD c4ebc1f, graph-only, `--tolerate-load-errors`): FAILED, Neptune out of memory
- Execution `run-20261116T201535Z-small`, 187 s, estimated spend 0.02 USD. The loader named the error: `NEPTUNE_LOAD_ERROR job=9 file=edges-COAUTHORED_WITH.csv code=OUT_OF_MEMORY_ERROR record=0 message=Out of memory error. Resume load and try again.`, `NEPTUNE_LOAD_ERRORS_TOTAL n=153760 named=1`. The policy refused it (out-of-memory is never tolerated), `LOADER_RESULT=FAILED`. The writer was a `db.t4g.medium` (4 GiB). Run 10 ran with `--tolerate-load-errors`, so `failOnError` was false. Run 10's `graph-report.json` in S3 (key prefix `20261116T201756Z`; the human read it with a filter that shows only the job statuses, so per-job counts were not read) lists 12 jobs: jobs 1 to 8 `LOAD_COMPLETED`, job 9 (`edges-COAUTHORED_WITH.csv`) `LOAD_FAILED` with 153,760 counted errors, and jobs 10 to 12 (`DERIVED_FROM`, `PUBLISHED_IN`, `RESOLVES_TO`) `LOAD_COMPLETED`. So the loader's hedge returned the `LOAD_FAILED` job instead of throwing when `failOnError` was false (`AwsNeptuneBulkLoader.scala`), the loop went on to jobs 10 to 12, and the rag policy rejected the result afterwards because of the out-of-memory code. Run 9 ran with `failOnError=true` and stopped at job 9. Run 9's three insert errors were very likely the same memory pressure (an inference: run 9 recorded no error detail).
- Re-sending data already loaded was judged safe from the AWS documentation (an existing node or relationship id is not updated and repeats are counted as duplicates), so the human chose to reload and recreate Neptune only if that failed.

## S run 11 (HEAD b456cd3, graph-only, `--tolerate-load-errors`): the graph loaded
- Execution `run-20261116T213222Z-small`, 280 s (4.7 min), estimated spend 0.08 USD (burn times time, not a bill). `FINAL_STATUS=SUCCEEDED` and, from the loader's own lines, `NEPTUNE_LOAD=LOADED vertices=32225 edges=135788 files=12 jobs=12` and `LOADER_RESULT=SUCCESS` (the clean word; no errors, no warnings). All 12 jobs ended `LOAD_COMPLETED` with `errors=0`.
- `edges-COAUTHORED_WITH.csv`, the file that failed twice, loaded with `records=1578576 duplicates=0 errors=0`. For the other 11 jobs `duplicates` equals `records`. This is consistent with those files having been loaded before, and the statuses support it: run 10's `graph-report.json` in S3 (read by the human with a status-only filter) lists jobs 1 to 8 (the seven vertex files and `edges-AUTHORED.csv`) and jobs 10 to 12 (`DERIVED_FROM`, `PUBLISHED_IN`, `RESOLVES_TO`) as `LOAD_COMPLETED`, so each of the 11 files with duplicates equal to records had completed a load in run 10, before run 11. Separately, by the loader's code (`AwsNeptuneBulkLoader.scala`: one job at a time, stop at the first failure that is not tolerated) and the run 9 log, run 9 (`failOnError=true`) stopped at job 9, which would mean jobs 1 to 8 had also completed in run 9; that is an inference, because run 9's report was not read. What is still inference, not read: that the earlier loads CAUSE run 11's duplicate counts (no per-job counts of run 10 were read, and the documented duplicate definition covers node rows only). `edges-COAUTHORED_WITH.csv` showing 0 duplicates in run 11, although run 9 had processed 92,256 records of it and run 10's job 9 failed again, is unexplained; it sits against the AWS statement quoted in the run 9 section that data loaded up to a failure persists, and no explanation has been verified. The release records carry the same wording (`docs/releases/phase-14/runs-s-6-to-11.md`).
- AWS documentation, read by the orchestrator (the Neptune loader Get-Status response page): for openCypher loads a duplicate is counted when a row in a NODE file has an ID equal to another row's or to an existing node's. It defines no duplicate count for relationship (edge) files, so the documented definition does not predict the non-zero duplicate counts Neptune reported for the edge files `AUTHORED`, `DERIVED_FROM`, `PUBLISHED_IN` and `RESOLVES_TO`; the reload explanation above is consistent with the counts but is not confirmed by the documentation.
- Sums from the 12 job lines (computed by the storage-engineer from the log, WO 116): 2,224,993 Neptune records processed, 646,417 of them reported as duplicates, so the loader's derived `inserted` is 1,578,576 and `unchanged` 646,417 (both property-level records, not vertices or edges; `inserted = records - duplicates - errors`, derived by the loader, not reported by Neptune).
- Inference, labelled as such: Neptune's `records` equals the file's rows times (non-empty properties + 1) for every file checked (`edges-COAUTHORED_WITH` 98,661 rows x 16 = 1,578,576; `edges-PUBLISHED_IN` 3,488 x 6; `edges-DERIVED_FROM` 3,556 x 6; `vertices-Venue` 1,342 x 6; `edges-RESOLVES_TO` 8,815 x 7), which says each file was parsed in full. It does not show that every row was stored.
- Per-job Neptune records (property-level): vertices AuthorMention 195,050, DatasetSnapshot 5, Institution 2,814, Researcher 60,875, Topic 2,838, Venue 8,052, Work 38,874; edges AUTHORED 233,940, COAUTHORED_WITH 1,578,576, DERIVED_FROM 21,336, PUBLISHED_IN 20,928, RESOLVES_TO 61,705. The loader's `vertices=32225 edges=135788` are the export's own counts (`exported.vertexCount` and `exported.edgeCount`, `AwsIngestMain.scala`), not counts taken from Neptune; nothing compares them with Neptune.
- Evidence limit: Neptune cannot be queried from outside its VPC and was destroyed without a snapshot, so the graph is evidenced by the loader's own log lines (`phase14-s-run-11-loader.log`); the reports `graph-report.json` and `graph-run.json` of run 11 exist in S3 under the run's loader prefix (prefix `20261116T213609Z`) but have not been read; only run 10's report was read, and only its job statuses. There is no independent query or count. What the logs establish: 12 jobs, one at a time, all `LOAD_COMPLETED` with 0 parsing, datatype and insert errors. Not established: that every row was inserted; the duplicate semantics; any independent count. Wording to use: "Neptune reported no errors for any of the 12 load jobs; duplicates equal records for 11 of the 12 files, which is consistent with those files having been loaded by the earlier attempts (an inference; the documented duplicate definition covers node rows only); no independent count exists."
