## Spark on YARN, from code
- Committed code overrode `spark-submit --master yarn`: `CollaborationPipeline.newSession` used `.master(config.master)` (default local[2]) and `JsonlExport.newSession` hard-coded local[2]. The uncommitted work order 18 edits fix both (see state below).
- Path surface: Spark, ER and JsonlExport use local java.nio Paths for `_work`, plans, summary, run-manifest, `_SUCCESS`, part renames (Export.renameParts, JsonlExport.finishParts) and input digests (Digests.directory), all on the driver. Spark reads and writes already pass toUri strings (Export.scala:164, JsonlExport.scala:425, :458, :491); the one bare path was Inputs.scala:144.
- Core nodes 0 (one node): containers run on the master, so driver-side renames, digests and `_SUCCESS` see the executors' files. This is Spark on YARN (spark-submit, ResourceManager, containers), not distributed execution; parallelism is bounded by one m5.xlarge.
- Multi-node: executors write parts to their own local disks, driver `Files.move`, `sha256File` and `_SUCCESS` fail or see a subset; inputs would not exist on other nodes. The scalability claim and Experiment B cannot be shown on 2 or more nodes with current code. One-node YARN shows YARN mechanics and per-stage metrics only.
- Smallest multi-node change: all Parquet and text I/O on hdfs:// or s3a:// URIs and all driver-side java.nio operations (rename, digest, `_SUCCESS`, manifests, deleteTree, listing) moved to the Hadoop FileSystem API; OutputPolicy, Digests, Export, JsonlExport change, and the Hadoop and ER tools must write to the shared filesystem too. A cross-module rewrite; a human decision.
- Both session builders hard-code `spark.driver.host` and `spark.driver.bindAddress` to 127.0.0.1: fine in client mode on one node, breaks multi-node client mode, may conflict in cluster mode (UNVERIFIED).

## Designs
- A (`emr-spark-8.0.0`, Spark 4.0.2-amzn-0, Scala 2.13.16, JDK 17): matches our Scala 2.13 / Spark 4.0 artifacts; ledger pins 4.0.5, so compile on 4.0.5 and run on 4.0.2 (API compatibility at patch level UNVERIFIED); Spark artifacts Provided; scala3-library_3 and our jars via `--jars`; interaction of `fs.defaultFS=file:///` with YARN staging UNVERIFIED. MapReduce on its YARN unconfirmed (no Hadoop application listed); fallback must be reported as "MapReduce in local mode on an EMR node". Whether Spark's bundled Hadoop client jars carry the MapReduce client classes (LocalJobRunner) is UNVERIFIED.
- B (emr-7.10.0 plus Spark 4.0.5 via `spark.yarn.archive`): archive is Spark's jars/ zipped (about 300-400 MB, UNVERIFIED), carries Scala 2.13 and Hadoop client 3.4.x against the cluster's 3.4.1 (likely compatible, UNVERIFIED); risks are `SPARK_HOME` and PATH conflicts with EMR's /usr/lib/spark (3.5) and its spark-defaults.conf; JDK 17 on emr-7.10.0 UNVERIFIED (a bootstrap action, JAVA_HOME and `spark.executorEnv.JAVA_HOME`, `spark.yarn.appMasterEnv.JAVA_HOME` would be needed if not). Hadoop as a normal MapReduce step on 3.4.1-amzn-2 with a jar carrying core, upickle and scala3-library_3 (fat jar means sbt-assembly and a new ledger key the human must approve, or `-libjars`).
- Spark jar form: thin jar plus lib/*.jar through `--jars` works in both; no fat jar needed for Spark. The 3.5.0 Hadoop client API against the cluster's 3.4.1 is UNVERIFIED (hadoop-engineer or smoke).

## Recommendation (spark-engineer)
Design A as primary, with a mandatory capability-check smoke before any S run. Reasons: matching Scala 2.13 and Spark 4.0 avoids B's stack of cluster-only assumptions; A needs no ledger change and no sbt-assembly for Spark; A's one big unknown (MapReduce on its YARN) can be settled in smoke with the local-mode fallback honestly worded. Choose B only if smoke shows MapReduce absent on A and the human requires distributed MapReduce.
- Human decisions: A or B; whether one-node YARN (not distributed execution) is acceptable for S or the S3A/HDFS rewrite for multi-node is in scope; accept 4.0.5-vs-4.0.2 for A; settle Hadoop 3.5.0 vs 3.4.1 API.
- Smoke additions: `spark-submit --master yarn --deploy-mode client` of a tiny Scala 3 main with `--jars scala3-library` (session, read and write one `file:` URI, print master and deployMode), then cluster mode (to see whether the 127.0.0.1 driver host breaks); record `SPARK_ON_YARN=<mode>`.
