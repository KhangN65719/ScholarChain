## D18: EMR release and job execution (human, via AskUserQuestion, 2026-11-14)
- Use `emr-spark-8.0.0` (Spark 4.0.2, Scala 2.13.16; listed in us-east-2 by the human's CLI check) with thin jars; no sbt-assembly, no ledger change. Terraform changes accepted: release label, applications list, EMR-service VPC endpoint with `ec2:CreateVpcEndpoint` (and `ec2:ModifyVpcEndpoint`) on the EMR service role, security-group 443 rules. The human reviews the IAM change at plan time.
- Spark: `spark-submit` on YARN (client or cluster mode), thin jars through `--jars` including scala3-library and our module jars; not `local[*]`. Experiment B and the scalability claim need YARN.
- Hadoop: the script step tries `hadoop jar` or `yarn jar` on the cluster's YARN first; if MapReduce is not available on this release, fall back to local mode and record it as "MapReduce in local mode on an EMR node". That check is part of the smoke step, so it is known before the S run.
- ER and the export run as plain java commands on the node.
- Orchestrator constraint to the decision (read from code by spark-engineer): Spark, ER and JsonlExport use java.nio Paths, so S runs on one node with `fs.defaultFS=file:///`; Spark on YARN with core nodes would write to each node's local disk and break. Multi-node YARN (for experiment B and M/L scalability) needs HDFS or S3A paths, a cross-module rewrite, and is NOT in this work. Work orders 17 (infra-engineer) and 18 (spark-engineer) implement D18 for the one-node case.
