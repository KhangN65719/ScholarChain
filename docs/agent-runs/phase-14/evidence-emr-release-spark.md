# Evidence: EMR release versus our Spark and Hadoop pins (orchestrator, AWS documentation MCP, 2026-11-14)

Source pages: docs.aws.amazon.com/emr/latest/ReleaseGuide/emr-7100-release.html (7.10.0 application versions), emr-release-app-versions-spark_8.x.html, emr-release-spark_8x.html. Read from the documentation, not observed on a cluster.

- Terraform emr module default `release_label` is emr-7.10.0 (build-engineer report 15, read from infra/terraform/modules/emr).
- emr-7.10.0 provides Spark 3.5.5-amzn-1, Hadoop 3.4.1-amzn-2, Scala 2.12.18, Python 3.9/3.11.
- Our ledger pins Spark 4.0.5 (spark-sql_2.13, Scala 2.13) and Hadoop 3.5.0 (project/DependencyVersions.scala, read by build-engineer). A Spark 4 / Scala 2.13 job cannot run on emr-7.10.0: this is a confirmed mismatch from the docs, not a packaging problem.
- Another release line exists: "AWS runtime for Apache Spark", release labels `emr-spark-8.0.0` (Spark 4.0.2-amzn-0, Scala 2.13.16, Python 3.11/3.13) and `emr-spark-8.1.0` (Spark 4.1.1, Scala 2.13.17, initial release 2026-09-08). The documentation says the 8.0.0 runtime is generally available on EMR Serverless, EMR on EC2 and EMR on EKS.
- NOT confirmed: whether an `emr-spark-8.x` EC2 cluster includes Hadoop MapReduce (the Hadoop job needs `hadoop jar`/MapReduce on the cluster); the version table showed no Hadoop row in the part read. Whether the Terraform `emr` module accepts an `emr-spark-*` release label (variable validation, applications list, security configuration) is not read. Hadoop 3.5.0 (ledger) versus the cluster's Hadoop is also open.
## Follow-up read of emr-spark-8.0.0 (orchestrator, AWS documentation, 2026-11-14)
- emr-spark-8.0.0 (initial release May 21, 2026): applications are only AmazonCloudWatchAgent, Delta, Hudi, Iceberg, JupyterEnterpriseGateway, Livy and Spark. Hadoop is not in the application list; the notes say Pig, Oozie, Tez, HBase, Flink, Trino and Presto are not included. The release is generally available on EC2, EKS and Serverless. Spark 4.0.2-amzn-0, Scala 2.13.16, JDK 17 default (21 available), Python 3.11. Its supported-region table lists US East (Ohio) in the Amazon Linux row for August 2026; the full list was truncated, so us-east-2 EC2 availability is read from that row only, not from the release-label listing.
- Consequences if we use it: (1) a `hadoop jar` MapReduce job may not be available on the cluster; running the Hadoop tool with plain `java -cp` in local mode using Spark's bundled Hadoop client jars is a possible route, UNVERIFIED; (2) EMRFS is removed (S3A instead); the AWS SDK v1 is removed; (3) private-subnet clusters need an EMR-service VPC endpoint (`aws.api.us-east-2.emr-service-cell01`): the emr_service role needs `ec2:CreateVpcEndpoint` and `ec2:ModifyVpcEndpoint`, the service access security group needs inbound 443 from the VPC CIDR, and the primary group outbound 443 to it; the 8443/9443 rules are no longer required. These are infra-engineer changes (an IAM change for the human to approve); (4) the 8 interface endpoints plan was written for emr-7.x.
- Downgrading Spark to the emr-7.10.0 line (3.5.5 on Scala 2.12.18): the orchestrator's reasoning, not a doc statement: a Scala 3 application cannot consume Scala 2.12 libraries, so a Spark 3.5 on 2.12 downgrade would not work for our Scala 3 jobs unless Spark is shipped with the job.
- Human-observed (2026-11-14): `aws emr list-release-labels --region us-east-2 --filters Prefix=emr-spark` returned `emr-spark-8.0.0` and `emr-spark-8.1.0`. An earlier `grep emr-spark` over the unfiltered list returned nothing because the CLI output was one page with a NextToken. Availability through the EMR API in us-east-2 is therefore observed; Hadoop MapReduce presence and Terraform module acceptance remain unconfirmed until the first CreateCluster.
- Simplification (orchestrator): run the pipeline as local-mode commands on the node (thin job jar plus lib/ copied from S3, `java -cp` with Spark's bundled Hadoop client jars on the classpath), which needs no fat jar and no sbt-assembly plugin or ledger key. UNVERIFIED: that Spark's jar directory carries the Hadoop client classes the Hadoop tool needs.
- Verification by the human, read-only: `aws emr list-release-labels --region us-east-2 --profile scholarchain` and, if the label is listed, a check that a cluster with that label has Hadoop (first CreateCluster confirms; the run-bounded pipeline's EMR stage would fail otherwise).
