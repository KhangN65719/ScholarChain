# Work order 45: infra-engineer, single-node permissions for YARN containers and compression defaults

Owner: infra-engineer. Same constraints as work orders 40 to 44 (scripts only, no apply, no commit, no ~/.aws). Sent as a follow-up message to the agent that did work order 44, so one report covers both.

Human intent: avoid spending another cluster launch (about 8 minutes, mostly provisioning) on two risks the agent reported in work order 44, task 5: (a) all data and outputs live under /home/hadoop/sc/run/<id>/ as file:/// paths, and on EMR the YARN containers (and the MapReduce output committer in the AM) may run as the yarn user; (b) EMR's mapred-site may default map-output compression to Snappy, which fails without native libraries.

Instructions given: before the hadoop stage record the user and the modes of /home/hadoop, $SC_HOME and the work directory; make the run directory usable by the yarn user (traverse bit on /home/hadoop and $SC_HOME, a+rX on the inputs, writable output parents, nothing outside $SC_HOME/run/<id> otherwise), print each chmod; record the effective io.compression.codecs and mapreduce compress settings as the node sees them; add -Dmapreduce.map.output.compress=false and -Dmapreduce.output.fileoutputformat.compress=false after checking the jobs' own settings.

Report received (author infra-engineer, summarized by the orchestrator):
- `mapreduce.map.output.compress=false` was NOT added: every job goes through `JobSupport.configureOutput`, which calls `JobConfig.enableIntermediateCompression(job)`, setting it true unconditionally, so a -D would be overwritten; the codec is set to DefaultCodec only when null, so an EMR Snappy default would win. Added instead `-Dmapreduce.map.output.compress.codec=org.apache.hadoop.io.compress.DefaultCodec`. Added `-Dmapreduce.output.fileoutputformat.compress=false` (the jobs write with TextOutputFormat through MultipleOutputs and never set output compression).
- Extra, beyond the order: `-Dfs.permissions.umask-mode=000` for Hadoop and `spark.hadoop.fs.permissions.umask-mode 000` in `write_spark_conf`, because Hadoop creates `_temporary` and `run=<id>` directories with mode 755 under the default umask 022; a umask only removes bits, so explicit-mode creations such as the 700 HDFS staging directory are unaffected. Untried lever.
- chmod set (each printed as a NOTE): `chmod a+x /home/hadoop /home/hadoop/sc`; `chmod -R a+rX $raw`; `chmod 1777` on the work directory and on the Spark and export output parents; failures are reported, never fatal. The post-stage `chmod -R a+rX` of outputs is kept and no longer aborts the run when an entry belongs to another user.
- Recorded as kv lines: PERMS_* (user, umask, modes of /home/hadoop, $SC_HOME, run dir and work directory before and after), NODE_CONF_* (io.compression.codecs, map-output compress and codec, output compress and codec, read from the site XML files, not `hdfs getconf`), HADOOP_OUT_FILE_OWNERS_MODES (owners of the files the jobs wrote). `capability-check.sh` has one added recording line (not being rerun).
- Unverified: whether the containers run as yarn; the untried umask lever; the regex-based NODE_CONF recording; a step killed by the EMR step timeout may not run the exit trap.
