# Reports 14 and 15 (condensed by the orchestrator; authors named per section). Both read-only; nothing executed.

## Report 15: build-engineer (job jars)
- packageJobs stages a thin jar plus lib/ per job module (hadoop, entityResolution, sparkAnalytics); no assembly plugin; no Main-Class. Missing at runtime on EMR: core, upickle family, scala3-library_3.
- Recommendation: sbt-assembly fat jar per job module with Hadoop and Spark Provided and Main-Class set; needs a new ledger key `sbtAssembly` whose version the human must approve (dependency-updater owns later values). `sbt check` and `sbt quick` unaffected. package.sh lines 225-239 require exactly one main jar plus lib/ and must change (infra-engineer).
- Loader image: services dependsOn core, storage, rag, so rag classes (IngestMain) are in target/docker-local/lib; no separate loader context needed. IngestMain.main existence was not read by build-engineer (spark-engineer read it: see below).
- HIGHEST RISK confirmed by the orchestrator in the AWS docs (evidence-emr-release-spark.md): emr-7.10.0 provides Spark 3.5.5 on Scala 2.12.18; our jars target Spark 4.0.5 on Scala 2.13. A different EMR release label is required.

## Report 14: spark-engineer (stage data flow)
- Order and arguments (read from source): Hadoop `scholarchain.hadoop.jobs.PipelineTool` `[-D...] <outputRoot> <dblpInput> [<dataset>=<path>...]`, with `-Dscholarchain.run.snapshots=...`; ER `scholarchain.er.ErBatch --run-root <snapshot=... dir> --out-root <dir>`; Spark `scholarchain.spark.CollaborationPipeline --er-run --hadoop-root --out-root [--master ...]`; `scholarchain.spark.JsonlExport <run dir> <out dir>` (a step the plan omitted); loader candidate `scholarchain.rag.IngestMain <exportDir> <outDir> [maxSummaryRows]`.
- Spark, JsonlExport and ER use java.nio.file.Path almost everywhere; reading s3:// would be a cross-module rewrite, not a small change. Recommended design (b): one EMR script step that copies inputs from S3 to local disk, runs the four tools against local paths (`fs.defaultFS=file:///` for Hadoop and Spark, `--master local[4]`), and copies results to S3. Runtime estimate (unmeasured): about 15 to 30 minutes at 3,472 works. Items UNVERIFIED: AWS CLI on the node, script step taking an S3 script path, disk space, `fs.defaultFS` behavior on EMR.
- THE CHAIN DOES NOT CLOSE TO AWS: `IngestMain` is documented "LOCAL ONLY" (LocalFsObjectStore, InMemoryVectorBucket, InMemoryDynamoTable, HashEmbedder, no AWS client; IngestMain.scala:10-14, 380-384). It reads a local export directory and loads nothing into S3 Vectors, DynamoDB or Neptune. Nothing read loads Neptune from the Parquet tables or `load-manifests/*.json` (they say planned-not-uploaded). Whether an AWS loader exists is UNVERIFIED (storage-engineer, report 12).
- Consequence for D2: an AWS-side S3 Vectors ingestion with working retrieval (Titan embeddings at 256 dimensions, S3 Vectors index) and a Neptune load need code that has not been confirmed to exist.
