## 1. Problem and motivation

Collaboration questions about scholarship ("who are the most connected researchers in a field and period, and how are two researchers linked?") cannot be answered from one source. Authorship records come from several bibliographic sources under different identifiers, the same person appears under several mentions, and a collaboration graph built without identity decisions overstates or understates every metric. A second problem sits on top of the first. A language model that is asked to describe the graph can state a number that no graph row supports. ScholarChain therefore separates the work into steps whose outputs can be inspected: Hadoop MapReduce prepares publication, author and link records; an entity-resolution step owns every match decision; Spark builds a temporal weighted coauthorship graph and collaboration metrics from accepted links only; loaders put the results in S3, Neptune, DynamoDB and S3 Vectors; and a runtime plans a query, retrieves graph and vector evidence, synthesizes an answer, verifies each claim against the evidence and returns the answer with an evidence bundle and an explain record, or abstains when the evidence does not support one (`README.md`, "Problem statement"; `CLAUDE.md`).

The constraints shaped the design as much as the question did. The project account has 20 USD of credit and a 20 USD spend limit, in one account locked to `us-east-2` (`infra/terraform/README.md`, "Account facts and cost limits"), so every expensive resource (Neptune, EMR, endpoints, Fargate tasks) exists only for a session and is destroyed afterwards. The project also has to be built by a factory of agents under rules that make each artifact have one writer, so the repository is organised around contracts and versioned artifacts rather than shared code (`CLAUDE.md`, "Module boundaries"). Sections 4 to 6 describe that factory; sections 7 to 15 describe the system it produced.

## 2. The three collaboration research questions and required metrics

The course text, appended verbatim to `docs/agent-runs/phase-17/prompt.md` ("Appendix: course text for final report section 2", added by Claude in chat, decision P17-29), states the central research problem:

> Which researchers have collaborated with the largest and most diverse sets of coauthors, how strongly connected are researchers through direct and indirect coauthorship relationships, and which researchers act as bridges between otherwise separate collaboration communities?

and decomposes it into three questions, quoted here as written:

1. "Which researchers have the broadest collaboration networks and which researchers publish papers with the largest author teams?"

## 4. Agentic software factory architecture

The project was built by 18 Claude Code subagents under one orchestrator session per phase. The shared rules are in `CLAUDE.md`; the ownership matrix is in `docs/agents.md`. Each subagent has a role file in `.claude/agents/` that fixes its model (`sonnet` for 17 roles, `opus` for `code-reviewer`) and its tool list (`README.md`, "Agent catalog"). Subagents never call one another; the orchestrator reads the project memory and the matrix, delegates each work order to the owning role with only the evidence it needs, and routes every repair (`docs/agents.md`, "Lifecycle routing"). Hooks under `.claude/hooks/` run in the client: a guard refuses dangerous commands, a test gate blocks a finish when sources are newer than the test marker, and a formatter runs on edited Scala files (`CLAUDE.md`, "Hook operation").

Each piece answers a failure that a coding agent has by default. An agent that can write anywhere will edit the file that makes its test pass; the matrix gives each artifact class one writer. An agent that reviews its own work approves it; the reviewer has only Read, Grep and Glob, returns APPROVE or REQUEST CHANGES and never fixes its own findings (`.claude/agents/code-reviewer.md` tool list in the catalog; `docs/agents.md`, "Approval and escalation"). An agent that is told to run tests may report that it ran them; the build writes `.claude/.last-test-run` only after format, compile and tests pass, and the stop hook compares it with the sources (`CLAUDE.md`). Conversation context drifts between phases; each phase therefore starts in a fresh session so the ratified repository state, not the transcript, is the starting point (`CLAUDE.md`, "Project rules").

Every phase leaves an evidence folder, `docs/agent-runs/phase-NN/`, holding the work order, the owner's report, test and review reports, repairs, the human's ratification, and, since Phase 17, `human-gate.md`, `commit.txt` and an `agent-report.md` index (`docs/agent-runs/README.md`; `README.md`, deliverable D03). ## 5. Authority and ownership design

The matrix assigns each path or artifact class to exactly one agent (`docs/agents.md`, "Ownership matrix"). The argument for it is the cost of the alternative: with a shared tree, a failing test invites an edit to the test or to someone else's code, and a reviewer cannot tell whose defect it is. The design therefore has three layers.

The first is the matrix itself, with boundary rules that resolve new paths before anyone writes to them. It worked as a gap detector. At the start of Phase 17 the plan found that `reports/**` had no owner although the course requires `reports/final-report.md`; under the boundary rules that blocked the report until the human ratified an assignment, which became decision P17-3 and a one-row change to `docs/agents.md` (`docs/agent-runs/phase-17/plan.md`, survey finding 7; decision P17-3). This document is written under that assignment.

The second is the hooks. The guard refuses direct dangerous commands and constitutional edits by anyone except factory-engineer, refuses every write by the reviewer, and confines factory-engineer, test-engineer, deploy-engineer and service-engineer to their paths; it is not a general per-owner path fence (`docs/threat-model.md` section 5, citing `policy.py:179-197`). The Claude Code sandbox denies reads of secret paths and writes to constitutional files (`.claude/settings.json`). Direct script probes and live interception are kept as separate evidence in the restart-probe records.

The third is a set of controls that the repository records as open. The main session can still do a specialist's work inline, because its events carry no agent type; `docs/agents.md` states this as an open, behaviour-only control. The factory parser counted 0 ownership violations from 0 lines while counting 150 hook or guard refusal events; the two counters measure different things and the evaluation draws no link between them (`experiments/EVALUATION.md` sections 2.1 and 2.3). Whether each hook fires automatically in a fresh session after the Phase 17 restart is NOT RECORDED: probes P1 to P4 were not relayed when this report was written (`docs/agent-runs/phase-17/human-commands.md`). The H-2 pre-checks recorded for the final guard files are `validate-agent-files.sh` 4 of 4 PASS, `--list-categories` printing 18 lines, and `hooks-guard.sh` `RESULT pass=114 fail=0`, run by Claude in chat on the files before commit `5157e0e`; no run on the committed tree is recorded (same file).

## 6. Human gates and repair loops

Human gates sit at the points where an agent's report is not enough. A constitutional change needs a factory draft, an independent read-only review, human ratification and a fresh orchestrator session before use. A phase ends with the human's `sbt clean check` (the agent's `sbt quick` is turn evidence only and passes a smaller set) and the human's acceptance, recorded in `ratification.md` with the commit that holds it. ## 8. Entity-resolution method and evaluation

Entity resolution is a separate module so that identity is decided in one place. Spark reads only accepted links, never the decisions or the gold set, and a key with conflicting accepted links fails the Spark run instead of letting Spark choose (`modules/spark/DESIGN.md`, "Inputs and identity"). The batch reads four Hadoop stage outputs of one run and writes `decisions/v1`, `accepted-links/v1` and a manifest with the SHA-256 of each output (`docs/data-lineage.md` section 2.3). Policy `scholarchain.er.policy/1.4.0` accepts a pair at or above 0.95 if its gates hold, rejects below 0.35, leaves the band between unresolved, and may ask an adjudicator only about pairs in the band [0.7, 0.95). Four paths decide: exact identifier, deterministic bibliographic, probabilistic and LLM-adjudicated. The thresholds are hand-set and were not tuned on the gold set (`experiments/EVALUATION.md` section 6.5.1; `docs/agent-runs/phase-05/ratification.md`). The adjudicator in the recorded evaluation is an offline stub that always abstains, so the LLM path decided nothing (6.5.2).

The evaluation is a 230-pair stratified gold set with blind human labels, ratified in Phase 5 and replayed in Phase 16. The replay reproduced the earlier report: pooled precision 1.000 (Wilson 95% interval [0.952, 1.000]), recall 0.802 [0.711, 0.869], F1 0.890, 0 of 230 decisions changed (`experiments/EVALUATION.md` section 6.5.1). The stratified bootstrap gives recall 0.802 [0.740, 0.875]; its precision interval is the degenerate [1.000, 1.000] because there were no false positives, and the report itself warns that fewer than 10 were available (6.5.2).

The results are as much a negative finding as a positive one. Recall comes from one path: the exact-identifier path accepted 77 of 78 gold-same pairs, the deterministic-bibliographic and probabilistic paths accepted 0 of 9 each, and the hard-common-name and clear-non-match strata have recall 0.000 (6.5.1, 6.5.2). About 12 gold-same pairs in the clear-non-match stratum are suspected mislabels from a fast labelling pass; the manifest names none (NOT IDENTIFIABLE), so a proxy set was used, giving recall 0.917 if they are removed or relabelled, which is a sensitivity figure and not an estimate (6.5.2; `docs/agent-runs/phase-05/ratification.md`). Pooled precision does not measure the probabilistic path, because the export excluded 5,766 same-name agreeing-context pairs (same file). On the tier S export, 0.6719 of 17,569 researcher nodes are `unlinked` and the unresolved-endpoint rate on coauthor edges is 0.8025 overall (6.5.2). These are descriptive counts; they do not say how many of those researchers are the same person, because no gold set covers tier S. The consequence for the graph appears in the next section.

## 9. Spark coauthorship graph, collaboration metrics, paths, communities, bridge analysis and temporal analytics

Spark is used because the questions need repeated joins, iteration and aggregation over windows, which suit its execution model better than MapReduce (`docs/agent-runs/phase-06/prompt.md`, course text, "Why"). The `sparkAnalytics` module (entry point `CollaborationPipeline`) runs these stages, each recorded with its plan and metrics: a canonical researcher and authorship builder; the temporal weighted coauthorship graph; per-researcher metrics; connected components by iterated label joins; communities by iterated label voting; a bridge stage over adjacency and community; coreness by iterated pruning; path evidence by breadth-first expansion over bounded levels with a walk back; sampled path-length estimates; temporal comparison between window slices; and semantic summaries built from computed data (`modules/spark/DESIGN.md`, "Stage DAG"). Communities: each node proposes the neighbour label with the largest total weight (smallest label on a tie, its own label if among the largest), only about half the nodes by a seeded hash adopt a proposal per pass, and a window is converged at the first pass with no differing proposal, so the result depends on the seed. Bridge: `crossCommunityDegree`, `crossCommunityStrength`, the numbers of distinct communities connected, and the participation coefficient 1 minus the sum over communities of (s_ic / s_i) squared, with s the weighted degree and 0 without coauthors; `bridgeScore` is the participation coefficient. These are local measures that depend on the community partition, and there is no betweenness centrality (`modules/spark/DESIGN.md:165-178`).

Several design choices follow from the problem. An unresolved mention stays its own node and is never merged by name, so the graph is conservative (`DESIGN.md`, "Identity rules"). A duplicate record of a canonical work adds nothing to any count. Windows default to `1900-1999, 2000-2004, 2005-2009, 2010-2014, 2015-2019, 2020-2029, all`, each window part of every key so windows run together (`DESIGN.md`, "Windows"). The run id is derived from the digests of every input, the configuration, the transform version `spark-analytics/1.1.0` and the SHA-256 of the module's main sources, so the same inputs under the same code give the same id. Driver collection is capped: the one `.collect()` in `modules/spark/src/main` is inside `DriverGuard.rows`, which fetches `cap + 1` rows and throws `RowCapExceeded` above the cap (`README.md`, "Known check findings", V01 and A01 item, citing `Support.scala:13-21`).

Results, from the export of experiment A (`graphchecks-a-export-2`): 17,569 researcher nodes, 3,556 work nodes, 98,661 coauthor edges (19,483 `coauthor:v1` and 79,178 `mention-coauthor:v1`, arithmetic equal to the total), 21,268 authored edges, 6,171 components, 6,663 communities and 41,885 semantic summaries; coauthor edges by window grow from 76 (1900-1999) to 36,486 (2020-2029) (`experiments/EVALUATION.md` sections 1.1 to 1.3). Integrity checks on that export read 0 duplicate ids in all 17 tables, 0 dangling endpoints, 0 edges without support, 0 provenance mismatches and 27 of 27 checked path hops present in the edge table; the human traced 10 DBLP-backed edges and found 10 of 10 correct (1.2). The checks read the export, not Neptune (1.4). The earlier Phase 6 local run `run:v1:fc4bbd1a-...` passed all 13 invariants (`docs/agent-runs/phase-06/ratification.md`).

The graph is fragmented, and the record says so plainly. On the Phase 6 subset run (`312ea79b-...`) the largest component held 148 of 17,490 nodes (0.85 percent) in 3,035 components (`modules/spark/DESIGN.md:201-203`; `phase-06/ratification.md:10`); the figure for the Phase 15 export is NOT DERIVED here. The cause given in the Phase 6 record is that conservative entity resolution leaves most mentions unresolved; 896 mentions with ORCIDs in integrity-failed clusters get no canonical id, and whether ORCID equality alone may merge them is an open policy question (`phase-06/ratification.md`). Paths and bridge scores therefore describe small components (`docs/architecture.md` section 7). The `path-evidence` table holds only 42 rows, a stated design limit of hub pairs (`experiments/LIMITATIONS.md`, L8). On AWS the whole pipeline step ran 3,526 s in experiment B and 61.3 minutes in experiment A (section 17). The Spark stage ran on one node on EMR; the bounded EMR Spark run of Phase 6 was deferred and replaced by a local run (`phase-06/ratification.md`).

## 10. Storage architecture

Four stores each serve one access pattern, and the argument for each is the pattern, not the product. S3 holds raw, curated, graph, semantic-context, reports and logs prefixes in two buckets; the Spark export is the hand-off between EMR and the loaders, and the Neptune CSV and its manifest live there too (`docs/architecture.md` section 5; `docs/data-lineage.md` section 2.5). Neptune (openCypher) holds the property graph for bounded multi-hop reads such as neighbours and shortest paths, loaded by CSV bulk load; it is created per session and destroyed after it, with no final snapshot in the course environment, so a session-down loses it by design and the graph is reloaded from S3 (`docs/threat-model.md` section 7). DynamoDB holds read models and audit: a run ledger, an entity-link cache, query sessions, evidence bundles, an artifact registry and a researcher metric cache, on demand, with no idle cost (`DynamoDb.scala:248-614` as cited in `docs/architecture.md` section 5). S3 Vectors holds semantic retrieval (section 11).

The load path was proven the hard way. Runs 6 to 10 of Phase 14 failed (loader step timed out; PutVectors rejected empty arrays; an out-of-memory error on the 1 GB loader task; a bulk-load failure with 3 insert errors; and a Neptune `OUT_OF_MEMORY_ERROR` on `db.t4g.medium` with 153,760 errors). Run 11 on `db.r6g.xlarge` succeeded with 12 bulk-load jobs `LOAD_COMPLETED` and 0 errors, and no single execution completed EMR, vector ingest and graph load together (`docs/releases/phase-14/README.md`, "Outcome in one table"). The Phase 15 reload of experiment A's export finished with `NEPTUNE_LOAD=LOADED vertices=32225 edges=135788` (`docs/releases/phase-15/README.md`), equal to the projected counts, with a difference of 0 and 0 (`experiments/EVALUATION.md` section 1.3). Whether the Neptune content equals the export row for row is UNVERIFIED: Neptune cannot be queried from outside the VPC and the load is evidenced by the loader's own report lines (`docs/releases/phase-14/README.md`, "What is and is not evidenced"). ## 11. S3 Vectors and optional OpenSearch design

Semantic retrieval searches Spark's semantic summaries. S3 Vectors was chosen as the vector store; the repository records its fit to the constraints rather than a comparison with OpenSearch. It has five versioned indexes (`researcher-profile-v1`, `collaboration-community-v1`, `paper-abstract-v1`, `collaboration-path-v1`, `topic-institution-summary-v1`, the last without a source), 256 dimensions, cosine, and keys that are the Spark `summaryId` hash, so a rerun gives the same key (`docs/data-lineage.md` section 2.5). Embeddings are Amazon Titan Text Embeddings V2, 256 dimensions, normalised, model version label `amazon.titan-embed-text-v2:0-d256-norm`; 256 is the cheapest dimension and is not changeable without destroying the vectors, which the Terraform module guards at plan time (`infra/terraform/README.md`, "S3 Vectors: changing the dimension destroys the vectors"). Writes are idempotent by text hash and model, and a changed text under an existing key is refused with `ChangedVectorContent` rather than overwritten. That refusal was observed on AWS in experiment F run 1 (`experiments/LIMITATIONS.md`, L10), where it turned a wrong template into an invalid experiment rather than silent corruption. A reason for choosing S3 Vectors over OpenSearch beyond cost and the optional status of OpenSearch is NOT RECORDED in the files read.

OpenSearch is not implemented. The Terraform README states "Not deployed" with no stub resource, and the experiment record says "No OpenSearch, so no fourth mode" (`infra/terraform/README.md`, section "OpenSearch"; `experiments/RESULTS.md` section 2, row 14). No hot tier or hybrid lexical retrieval was built or evaluated.

How S3 Vectors performed is in sections 17 and 18. In short: vector retrieval is weak on this benchmark (recall at K = 10 of 0.1498 against 0.4935 for graph) and, under load, the vector stage was the slow stage (p50 3,250 ms at 48 clients against about 4 ms for graph retrieval), with the cause UNVERIFIED. The vector index also carries a provenance caveat: vectors come from an earlier ingest and the graph from experiment A, and 2,000 vector keys were deleted after experiment E (`experiments/LIMITATIONS.md`, L9 and L12).

## 12. Runtime collaboration-analysis agents

The runtime workflow is a set of components in `modules/rag`, specified in the Phase 9 order as numbered roles. Roles 2 to 10, read for this report, are a researcher resolver, a metrics retriever, a path finder, a community analyst, a semantic-context retriever, an evidence builder, an answer synthesizer, a claim verifier and an audit stage (`docs/agent-runs/phase-09/prompt.md`, lines 30-71); the planner is the `planning` stage below. They run in-process behind the slow service; the timed stages are `planning`, `graph-retrieval`, `vector-retrieval`, `fusion`, `synthesis` and `verification`, and the retrieval modes are `graph`, `vector` and `fused`, the default being `fused` (`docs/architecture.md` section 3). They are not separate deployed agents; section 13 explains why.

The design rules are the ones that make an LLM answer checkable. Graph retrieval is deterministic and parameterised openCypher; user text cannot become database code (the Phase 9 gate). Every number an agent states comes from the graph or metric stores with evidence pointers, never from vector snippets; the verifier rejects a numeric claim whose only support is a semantic-context item (Phase 9 scope note, decision F1). Each claim cites evidence ids that must resolve inside the answer's own bundle, a claim with status Verified needs evidence, and a non-verified claim with no evidence must state uncertainty (`docs/data-lineage.md` section 2.6, citing `Contracts.scala:484-500`). The verifier returns VERIFIED, PARTIALLY_SUPPORTED, UNSUPPORTED or CONFLICTING. Ambiguous researcher names abstain rather than resolve silently. The answer model replies under a JSON schema with a bounded repair (2 retries); prompts are versioned (`planner-classify` 1.0.0 and `synthesis` 1.2.0, `modules/rag/src/main/scala/scholarchain/rag/Model.scala:64-88` as cited in `README.md`, D10); retrieved text enters the model only under `untrusted` keys, and an injection screen with seven patterns flags and does not refuse (`docs/threat-model.md` section 2).

The behaviour of these rules is measured in section 18. Two facts belong here. The answer model defaults to an offline `stub` when unset, and a Bedrock model id is required when the model is `bedrock` (`docs/architecture.md` section 3), which let every experiment and unit test run without a paid model. And the synthesis prompt's claim cap exists because of a measured failure (section 18).

## 13. Microservice architecture and API

Two HTTP servers share one image and run as two ECS Fargate task definitions: a fast read service on port 8080 (evidence, graph nodes and neighbours, explain, metrics, health) and a slow query service on port 8081 (query, jobs and results, health). Each has its own pool, executor and desired count, so a slow synthesis cannot starve an evidence lookup (`docs/api.md` sections 1 and 4; `infra/terraform/README.md`, "Consolidation (runtime)"). The route set is `POST /v1/query`, `GET /v1/jobs/{id}` and `/result` on the slow service, and `GET /v1/evidence/{id}`, `/v1/graph/nodes/{id}`, `/v1/graph/nodes/{id}/neighbors`, `/v1/explain/{id}`, `/metrics`, `/healthz` and `/readyz` on the fast service (`docs/api.md` section 4, with `Routes.scala` line references). Access is by two static bearer scopes (query and read) injected as environment variables from Secrets Manager (`docs/api.md` section 2; `AwsRuntime.scala:29-32`).

Limits are bounded and typed: HTTP pool 8 threads with queue 64, call pool 16 with queue 32, body limit 65,536 bytes, question limit 1,000 characters, deadlines of 2 s (fast) and 10 s (slow), at most 2 retries for idempotent reads and a circuit breaker opening after 5 failures for 5 s; overflow returns a typed error rather than hanging (`docs/threat-model.md` section 6, citing `ServiceConfig.scala:124-152`). A query returns an answer, claims, an evidence bundle and a query id, and the evidence and explain endpoints return each evidence item with its source record and provenance and the plan, stage times, prompts (id, version, hash), models, score components and verification report (`docs/data-lineage.md` section 2.6).

Retrieval, ranking, synthesis and verification are not separate services. The design runs them in-process behind the slow server because they have no network seam, which saves a hop and a deployment per component and costs the separate scaling rows of the course. The experiment record states it as NOT MET for a separately scaled vector retriever, rank service and synthesis service (`experiments/RESULTS.md` section 2, rows 19 and 20). Two further limits shape use. There is no public ingress; a client reaches the services from inside the VPC, and the internal load balancer listens on HTTP 80, an accepted risk the human is to confirm (`docs/threat-model.md` section 4, last row). Query records and idempotency are in process, so evidence and explain lookups work only while the answer is in a bounded in-memory index (`records.retained` default 500, `ServiceConfig.scala:151`), although the durable copy is in DynamoDB (`docs/data-lineage.md` section 2.6). The filters `topic`, `venue` and `institution` are validated and refused with 422 (`docs/architecture.md` section 6).

## 16. Security and threat model

The threat model covers seven classes. Each is summarised with the strongest control and the largest gap; the tables with file and line evidence are in [docs/threat-model.md](../docs/threat-model.md).

- Prompt injection. Untrusted text reaches the model only under `untrusted` keys, a seven-pattern screen flags (not refuses) instruction-like text, the model's reply must pass its schema, and claims are verified against the bundle. The gap is that the prompt is a request, the screen is a pattern list with no recorded false-negative rate, and Haiku's behaviour under injection was not measured as its own experiment (NOT RECORDED).
- Data poisoning. Hadoop rejects and counts malformed records; entity resolution owns identity; the export carries a manifest with per-file size, SHA-256 and rows; the runtime refuses an export whose `sourceRunId` differs from the configured graph run; vector writes are idempotent and refuse changed content; experiment F2 showed a poison queue message received three times, never written and dead-lettered. The gap is that the manifest and the files share one bucket and writer, and no deliberately poisoned source pair was tested.
- Credential exposure. Secrets come from Secrets Manager; Terraform creates them empty; the sandbox denies reads of secret paths; scripts scan for key material; tests build fake keys at runtime so no key-shaped literal sits in the tree; `.mcp.json` holds a `${VAR}` reference. The gaps: a human fills the secrets with a command whose arguments are briefly visible locally, the HTTP listener is unencrypted inside the VPC, and a fake key literal remains in git history (`README.md`, "Known check findings").
- Over-permission. One IAM role per function with ARN-scoped actions, no `bedrock:*`, and a runtime that cannot write the ledger, registry or vector indexes. The gaps: `ecr:GetAuthorizationToken` and `RunJobFlow` need `*`; the human's credentials that run the scripts are broad, so the control is the approval record; and the Neptune read-only condition key behaviour on a live path is UNVERIFIED.
- Denial of service. ## 22. Threats to validity

## 24. Lessons learned

These are the author's reading of the evidence cited, not recorded conclusions.

Make the gate test the thing that matters. The Phase 15 smoke printed PASS while every answer abstained because it tested status and counts; the first audit run, `h-audit-1`, was wrong because of a metric-name defect that review 14 found (`experiments/EVALUATION.md:611`). A check that cannot fail for the failure you care about is a status light (`experiments/LIMITATIONS.md` L14 and L17; `docs/evaluation.md` section 5, item 12).

Stubs buy cheap development and hide the expensive truth. The offline answer model let every phase run for nothing and let the load experiments measure the retrieval path, and it also meant no Haiku latency existed until Phase 16, by which time the 10 s deadline default was already wrong (`docs/evaluation.md` sections 2.5 and 6).

One writer per artifact is worth its overhead, and it also finds gaps. The ownership map found the unowned `reports/` path before anything was written there, and the reviewer-never-fixes rule is why repairs have records at all. Its limit is honest too: the main session can bypass it, and the Phase 4 repair by Codex held the rule only nominally (sections 4 and 5).

Identity is the hard part of a collaboration graph. The strongest metrics in the evaluation, ranking nDCG of 1.0 and a structural support rate of 1, say nothing about identity; the weakest results, a 28% false-abstention rate mostly from unresolved identity and a graph in which 80% of coauthor edges have an unresolved endpoint, are where the real work remains (sections 8 and 18).

Measure against something that was not built from the same data. Labels, retrieval and audit shared one export, so they agree by construction; the 10-edge DBLP check and the 230 blind gold labels are the only checks that touched an outside source (`docs/evaluation.md` section 3.6).

Records drift, and drift has a cost. Report formats changed by phase, which made the process counts approximate and the archived reports fail the automated format check; one reporting form from the start would have cost less than the Phase 17 compilation of indexes (`docs/evaluation.md` section 3.8; `README.md`, "Known check findings").

Run the expensive thing once, under a ceiling, and write down the failures. Five failed loader runs in Phase 14 produced the sizing; the approval record and the cost gate (billed + lag reserve + the session's high estimate at most the stop) stopped any single session from consuming the margin.
