## Window rules (Phase 11 repair 1, M-1)

With a structured `window` on a query, `compose` mirrors the planner's window reader (`Planner.windowsOf` is `private[rag]`, so services keep a copy, D7). The rules: if the planner reads no window and no stray year is in the question, " from S-E" is appended; if the planner reads exactly the structured window and no stray year, the question passes unchanged; anything else is 422 UNSUPPORTED_CONSTRAINT. A count ("top 1000 coauthors") is not a year. Repair 2 (N-1): the appended clause is zero-padded to four digits (`from 0001-2009`), because the planner reads only four-digit years and a start year below 1000 used to fall back to the default window 1-9999 while the response echoed the structured one. `request.window` equals the window the planner applied, or the request is refused, for every shape in the `Phase11WindowAgreementSuite` tables. `Phase11WindowAgreementSuite` passes 5 of 5 in the repair round 2 `sbt quick` (was 3), and the whole quick run totals 962 passed, 0 failed. That is a tested guarantee over those shapes, not a proof for all inputs: the copy of the reader in services can still drift from `Planner.windowsOf`. The suite guards against drift end to end, reading the applied window from the explain endpoint's plan. It now also covers the windows (1, 2009), (500, 1500), (999, 2009), (1, 9999), (1000, 2009) and (2000, 9999), each with no window in the question, a matching window (padded) and a conflicting one, and a separate test requires 200 (no over-refusal) for each of the six with a no-window question.
