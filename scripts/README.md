## From a clean checkout

The exact sequence the README reproduction section and the demonstration use. Every line runs without AWS credentials (sbt and the Terraform provider download need network access). Replace `<id>` with the approved 12-digit account and give `--out-dir` an absolute path outside the repository.

```
git clone <repository-url> ScholarChain && cd ScholarChain
bash scripts/check.sh --dry-run
bash scripts/check.sh                       # prerequisites: bash, git, python3, shellcheck, JDK 21, sbt, terraform
bash scripts/package.sh --dry-run
bash scripts/package.sh --out-dir /abs/outside/repo/package-1   # prerequisite: Docker with a running engine, unless --skip-images
bash scripts/archive-evidence.sh --dry-run --include /abs/outside/repo/package-1
bash scripts/archive-evidence.sh --include /abs/outside/repo/package-1

```

Prerequisites in one place: bash 3.2 or later, git, python3, shellcheck, JDK 21, sbt, Terraform, and Docker with a running engine for `package.sh` (not needed with `--skip-images`, and not for any dry run). The live scripts also need the AWS CLI and curl.

`check.sh --skip-sbt --skip-terraform` is the fast form for a machine without sbt or Terraform; its summary says what was skipped, and its last line is `CHECK_RESULT=PASS_WITH_SKIPS`, never `PASS`. ## Dry run

`--dry-run` is a flag and nothing else: no environment variable turns it on, and no flag turns it off again. It works with no AWS credentials, no network and no Terraform state. It was added in Phase 13. The harness (check run 3, `RESULT pass=546 fail=0`) exercised it for every script with stub `aws`, `terraform`, `docker`, `curl` and `sbt` first on `PATH`, and the tripwire over the whole run saw no stub reached (`checks-3.md`). That is observed for the harness's cases only; a dry run has not been tried against any real cloud, and the guarantee stays the code reading above.

How a dry run cannot reach the cloud. `lib.sh` defines `aws`, `terraform`, `docker`, `curl` and `sbt` as shell functions. Each starts with `dry_guard`, which stops the script with `EVIDENCE: DRY_RUN_GUARD ...` when a dry run reaches it, so every call site in every script is guarded, also inside `$( )` and pipelines. `consume_approval`, `make_out_dir` and `write_meta` carry the same guard. The real binary is found with `type -P` and run by path. Each script also leaves through `dry_finish` before its first real call. `require_cmd` skips `aws terraform docker curl sbt` in a dry run and uses `type -P` otherwise, because `command -v` would find the wrapper functions.

Every dry run prints, on stdout, `DRY_RUN=yes` first, then after the parameters pass `TARGET_ACCOUNT=`, `TARGET_REGION=`, `TARGET_ENVIRONMENT=` (all from the arguments), `IDENTITY_CHECK=skipped`, `ACTION=`, `SCRIPT_DIGEST=` and `ARGS_DIGEST=`, then `STEP[n] name: dry-run` for each step it would run, using the real step names and numbers, and `WOULD_RUN:` lines with the commands as text. Steps that really run locally in a dry run (parameter validation, the clean-tree check, plan binding when the plan file exists, the approval record, the input scan of the pipeline) print `start` and `ok` like a real run.

Approval-gated scripts (`deploy`, `rollback`, `run-bounded-pipeline`, `smoke-test`, `cleanup` apply modes) still require `--approval-record` and run the full verification (fields, digests, expiry, 24 hour window, cost ceiling, account and Region, stateful acknowledgement, already consumed). `verify_approval` takes the stateful-acknowledgement requirement as an optional fifth argument (`yes`; default `no`) and checks `STATEFUL_CHANGE_ACKNOWLEDGED=yes` after every other check and before it prints `APPROVAL_VERIFIED`, so a record without the acknowledgement is refused without that marker (`cleanup.sh` passes `yes` for `apply-destroy`, in the dry-run and the real branch; work order 09, observed by harness case `5.cleanup-destroy.destroy-without-stateful-ack` in check run 3). `deploy.sh` and `rollback.sh` image mode pass `yes` too whenever the plan's `.meta` says `STATEFUL_CHANGE=yes` (work order 15, repair of review finding R3; its dry-run and refusal paths were observed in the 570-case harness run, `checks-5.md`; no real run), so a record without the acknowledgement is refused before `APPROVAL_VERIFIED` is printed; when the plan metadata is not available (a dry run without the plan file) the argument is `no` and the acknowledgement check is reported as skipped, as before. A dry run prints `APPROVAL_VERIFIED`, then `APPROVAL_SKIPPED_FIELDS=` and `APPROVAL_NOT_CONSUMED dry-run`, and never calls `consume_approval`, so the record stays usable. A missing, expired, mismatched or consumed record is refused with a nonzero exit and `EVIDENCE:` on stderr, as in a real run. The clean-tree check is also refused as in a real run: a dry run of `deploy` or `rollback` image mode on a dirty tree stops.

What a dry run cannot do, and says so. `deploy` and `rollback` image mode need the saved plan file and `deploy` needs both build contexts. The arguments are still required. When the plan file or its `.meta` is missing, plan binding, the plan digest and the stateful acknowledgement are skipped (`CHECK_SKIPPED`, `APPROVAL_CHECK_SKIPPED field=PLAN_DIGEST`). When the plan or a context directory is missing for `deploy`, the platform and context digests are unknown, so `ARGS_DIGEST` is printed as `unavailable` and that record field is not compared. `APPROVAL_SKIPPED_FIELDS` lists every record field not compared; a skipped check is never reported as passed. `--print-digest` still needs all of them and refuses when they are missing.

`plan.sh` takes no record: its dry run prints the target and the Terraform commands as text and exits 0.

`cleanup.sh` order of checks, the same in a real run and a dry run, with every refusal before anything is listed: (1) `human-invocation`: `--i-am-the-human`, `SCHOLARCHAIN_AGENT_RUN`, terminal check; (2) `validate-params`: mode, shared parameters, `course` only, `cleanup.tfvars`, image tag, `--plan-file`, `--acknowledge-data-loss`; (3) plan binding and the approval record (apply modes); (4) only then the listing. The human-only refusals apply to a dry run too, so an agent invocation is refused at step 1; that is how an agent proves the refusals. The listing is printed only for a human invocation. It reads the Terraform source files, labelled `SOURCE=terraform-source (not live)`: the lines of `environments/course/main.tf` that read `cleanup_mode`, the stateful resources declared in `modules/*/main.tf` (S3 buckets, DynamoDB tables, S3 Vectors bucket and indexes, ECR repositories, Neptune cluster and instance, secrets) with their name expressions and the attributes the flip changes. Names are source expressions with `var.`, `local.` and `each.` references unresolved. The live listing (`terraform state list`, bucket outputs, first 20 keys) runs only at real execution.

## Exit codes

Existing codes are unchanged. Every refusal and failed check in these scripts goes through `die`, which exits 1, so the scripts do not distinguish a usage error from a refusal or a failed gate by exit code. They are told apart by the `EVIDENCE:` text on stderr. A split into 2, 3 and 4 was not made, because renumbering `die` would change the real paths.

| Code | Meaning |
|---|---|
| 0 | success, `--help`, `--print-digest`, a dry run that passed, or `check.sh` with `CHECK_RESULT=PASS` or `CHECK_RESULT=PASS_WITH_SKIPS` (every gate that ran passed; a skipped gate is not a pass) |
| 1 | any refusal or failure through `die`: bad or missing argument, unknown flag, refused approval record, failed check, `DRY_RUN_GUARD`, a failed gate; also `exit 1` in `require_clean_tree` |
| 124 | a docker or sbt command, or an experiment entry point, exceeded its time limit (`run_bounded`) |
| 130 | `run-bounded-pipeline.sh` interrupted by INT or TERM after it stopped the execution and any cluster it created; `run-experiment.sh` interrupted outside the entry-point run (its record then ends `FINAL_STATUS=INTERRUPTED` with no `RECORD_COMPLETE`). A signal during the entry-point run goes to the entry point and the script finishes the record |
| other | the exit status of a failing tool under `set -e` (for example `terraform fmt -check` exits 3 on unformatted files, and `terraform plan` 1); the scripts do not translate it |

## Timeouts and retries

Every `aws` call goes through the wrapper in `lib.sh`: `--cli-connect-timeout 10 --cli-read-timeout 60`, and `AWS_MAX_ATTEMPTS=3` only for operations named `describe-*`, `list-*`, `get-*` and `head-*` (idempotent reads); every other operation (`start-execution`, `stop-execution`, `terminate-job-flows`, `invoke-model`, `converse`) runs once. Before Phase 13 the calls had the CLI defaults (60 s timeouts, standard retry of 3 attempts for every operation). `docker login` is limited to 120 s and `docker build` and `push` to 1800 s each by `run_bounded`, which stops the command with TERM and then KILL; they were unbounded before. Since work order 15 (review finding R2) `run_bounded` runs the command in its own process group (bash job control, `set -m`, which bash 3.2 supports) and sends TERM, then KILL 5 s later, to the whole group, not to one PID. When the command returns, any member of the group still alive is stopped the same way before `run_bounded` returns, so no child keeps running or writing afterwards (`SC_RB_STRAY=1` records that it happened, `SC_RB_LEFT=1` that a member survived KILL, with an `EVIDENCE: PROCESS_GROUP_REMAINING` line). A process that starts its own session or group (`setsid`, `set -m` in the entry point) is outside the group and is not reached. The same change makes the 124 exit status depend on a timeout marker file, not on how the command exits: the watchdog creates the marker when the limit fires, and `run_bounded` returns 124 whenever the marker exists, whatever the command's own status was, including 0 (repair round 3, S1). A command that exits on TERM, needs KILL, or catches TERM and exits 0 after the limit all return 124; before, 124 came back only when KILL was needed (and later only for a nonzero status). A command that fails by itself before the limit keeps its own status. A run whose entry point exits 0 after the limit is therefore recorded as `STOPPED_WALL_CLOCK`, not `COMPLETED`. This is written from the code and UNVERIFIED with real processes (the harness cannot reach it). `curl` calls keep their `--max-time` (10 s, 60 s for the query) and are not retried. `terraform` calls have no time limit, only `-lock-timeout=60s` on plan and apply: a killed `apply` can leave a partial apply and a held lock, so the operator interrupts it by hand. The `run_bounded` wrapper and the retry choice are UNVERIFIED with a real docker or sbt process and a real AWS call (see "Checks the human runs"); the harness ran the scripts only with stubs.

## Approval record

A plain `KEY=VALUE` file, `#` comments allowed, no spaces in values, every key exactly once, no other keys. It is parsed, never sourced.

| Field | Meaning |
|---|---|
| `APPROVAL_VERSION` | `1` |
| `ACTION` | `deploy`, `rollback`, `pipeline`, `cleanup`, `smoke-test`, `experiment`, `archive` or `upload`. `verify_approval` takes the action as a parameter and compares it with the record, so `experiment`, `archive` and `upload` needed no new allow list and no existing check was relaxed. (Work order 20 asked for `upload` to be added to an allow list in `lib.sh`; `lib.sh` has none, so `lib.sh` is unchanged and this row is the only registration.) For `upload`, `ARGS_DIGEST` covers the snapshot, both bucket names, the object and byte counts and limits, and one digest over every destination with its sha256 and size |
| `ENVIRONMENT`, `ACCOUNT_ID`, `REGION` | must equal the parameters; region must be `us-east-2` |
| `COST_CEILING_USD` | must equal `--cost-ceiling-usd` and be <= 20 |
| `PLAN_DIGEST` | sha256 of the saved plan file (printed by `plan.sh`), or `n/a` for `pipeline`, `smoke-test`, `experiment` and `archive` and for state-version rollback |
| `SCRIPT_DIGEST` | sha256 of the script file followed by `lib.sh`. Any edit to either invalidates the record |
| `ARGS_DIGEST` | sha256 of the exact canonical arguments (`--print-digest` shows the string). For `deploy` the arguments include the image tag, the docker platform and a content digest of each build context directory. For `experiment` they include the sha256 of the manifest file, the experiment id, the tier and the limits. For `archive` they include the S3 prefix, the evidence directory name and the sha256 of its `MANIFEST.sha256` |
| `GIT_SHA` | the commit the plan was made from (`deploy`, image-tag `rollback`) or the commit the experiment runs at (`experiment`), else `n/a` |
| `STATEFUL_CHANGE_ACKNOWLEDGED` | `yes` or `no`. A plan that destroys or replaces a stateful resource needs `yes`, as does `cleanup` destroy |
| `APPROVED_BY` | the human. Names that look like an agent or role are refused (a weak check; the real control is that a human writes the file) |
| `APPROVED_AT`, `EXPIRES_AT` | UTC like `2026-11-20T15:04:05Z`. `APPROVED_AT` not in the future, `EXPIRES_AT` not past, and **`EXPIRES_AT` at most 24 hours after `APPROVED_AT`** (`SC_APPROVAL_MAX_SECONDS` in `lib.sh`) |

Single use. Each apply-class script calls `consume_approval` after the record, plan binding and identity checks pass and just before its first billable or state-changing call. It makes a marker directory `${SCHOLARCHAIN_OPS_STATE_DIR:-$HOME/.scholarchain-ops}/consumed/<sha256 of action, ARGS_DIGEST, PLAN_DIGEST and APPROVED_AT>`; `mkdir` is atomic, so a second use of the same record, or a racing second run, is refused with "already consumed". A run that fails after the marker is written still consumes the record: a retry needs a new record (conservative, because a retry can re-spend). `smoke-test` and `pipeline` consume at their first call as well. `plan.sh` takes no record.

What this does and does not stop. It stops an accidental or scripted second run of the same record, a stale record lying around for weeks, and a record reused after a failed run. It does **not** stop a caller who can write a record: every digest is printable with `--print-digest`, so a caller can write a new record with a fresh `APPROVED_AT`, which is a new marker. The real control is the human signing the digest. A ratified launcher that verifies the approval record itself is not part of Phase 13 (decision D3, an open constitutional item) and remains a human-controlled step. The checks in these scripts are consistency checks, not authorization.

Two more things it does **not** stop (review 2, finding L-e):

- `SCHOLARCHAIN_OPS_STATE_DIR` pointing at an empty marker directory. The single-use markers are only directories under that path, so any caller who sets the variable to a fresh directory makes a consumed record usable again. A small hardening was added: `check_state_dir` (called by `verify_approval` and `consume_approval`) refuses a relative path, `.` or `..` segments, and a location inside the repository or `--out-dir`, and prints `STATE_DIR_OVERRIDE=<path>` when the variable is used so the override is visible in the log. It cannot refuse an empty directory elsewhere (for example a new directory under `HOME`), because the script has no way to know which directory held the earlier markers.
- The `smoke-test.sh` `--out-dir` repository check. It was a plain string-prefix match, which a symlink into the repository, a doubled slash or a different letter case on macOS (a case-insensitive file system) got past. It now compares physical paths with letter case ignored (`physical_path` and `path_within` in `lib.sh`): symlinks in the existing part of the path are resolved, doubled slashes are squeezed, and `.` and `..` segments and relative paths are refused. It is still a check at one moment: a symlink swapped after the check, a hard link or a bind mount gets past it. It is exercised by harness cases `5.smoke.out-dir-*` (a symlink into the repository, a `//` path and a case-changed path), which passed in check run 3 (`RESULT pass=546 fail=0`, `checks-3.md`). That is a first test, not a defence against a symlink swapped after the check, a hard link or a bind mount.

### `run-experiment.sh` and the experiment manifest contract

Runs one approved experiment manifest. Required: `--manifest`, `--approval-record`, `--environment`, `--account-id`, `--region` (us-east-2 only) and `--cost-ceiling-usd`; `--dry-run` and `--print-digest` as elsewhere. A record without `RECORD_COMPLETE` is an unfinished run (for example killed by SIGKILL). Metric locations: `METRIC_REGION`, `METRIC_NAMESPACES`, `METRIC_NAMES`, the window `METRIC_WINDOW_START_UTC` to `METRIC_WINDOW_END_UTC`, and `METRICS_DIR` with one `aws cloudwatch list-metrics` listing per namespace and name (a read, retried up to 3 times). The script does not pull metric series; pulling them from the window is a later step. `raw/` and `metrics/` are made read-only and `SHA256SUMS` lists every file. The directory is never reused: a second run gets a new id, and an existing directory is refused. Read-only bits are not a security control (the owner can change them).

Process group (review finding R2, work order 15). The entry point runs through `run_bounded` (see "Timeouts and retries"), so it is the leader of its own process group and TERM, then KILL 5 s later, go to the whole group, not to the one `env` or `bash` PID as before. Before `finalize` makes `raw/` read-only and writes `SHA256SUMS`, `run_bounded` has stopped every group member still alive, so nothing the entry point started writes to `raw/` afterwards; `finalize` records `ENTRY_PROCESSES_STRAY` and `ENTRY_PROCESSES_REMAINING`, and the script prints `ENTRY_PROCESSES_STRAY` or `ENTRY_PROCESSES_REMAINING` when they apply. If a member survived KILL the run still finalizes, then fails with `ENTRY_PROCESSES_REMAINING=yes` in the record, and the human must treat the checksums of `raw/` as unreliable. Limits: a child that leaves the group (`setsid`, its own `set -m`, a daemon that double-forks into a new session) is not reached; an `sbt` entry point stops the launcher script and its group, and whether the JVM it started is in that group is UNVERIFIED. Entry points should still trap TERM to clean up after themselves; an entry point that traps TERM and exits 0 after the limit is still recorded as `STOPPED_WALL_CLOCK` (exit status 124), not `COMPLETED`, because the timeout marker decides. UNVERIFIED until a real run: this was written from the code and the bash manual, not run with real processes.

## Phase 14: real docker login and build

How the scripts build, tag and log in (read from `scripts/package.sh`, `scripts/deploy.sh` and `scripts/lib.sh`):

- Tag. Both scripts take the full 40-character Git SHA of HEAD (`git_head`, checked by `require_image_tag`). `package.sh` builds `scholarchain-services:<sha>` and `scholarchain-loader:<sha>` locally, with `--platform` (`linux/amd64` for `X86_64`, `linux/arm64` for `ARM64`) and the labels `org.opencontainers.image.revision=<sha>` and `scholarchain.dirty=yes|no`. A dirty tree or detached HEAD is refused unless `--allow-dirty`; the tag is then `<sha>-dirty` or `<sha>-detached`, and `deploy.sh` refuses such a tree and such a tag. `deploy.sh` builds and tags its own images as `<account>.dkr.ecr.us-east-2.amazonaws.com/scholarchain-course-services:<sha>` and `...-loader:<sha>` from `target/docker-local`; it does not retag the `package.sh` images. An existing immutable ECR tag is reused, not rebuilt. So a `package.sh` image proves the Docker build works; it is not the image that is pushed.
- What the build runs. One process, `sbt packageJobs dockerLocal` (3000 s limit), which also builds `scholarchain-local:phase-2` for the host architecture, then `docker build` twice (1800 s limit each, through `run_bounded`). The base image in `Dockerfile` is pinned by digest and is pulled from its registry over the network. The Dockerfile only copies `lib/`, so the build runs no emulated instruction when the target platform differs from the host.
- Cost ceiling and approval. `package.sh` has neither: it takes no `--cost-ceiling-usd`, no `--account-id`, no `--approval-record` and no AWS credential, and makes no AWS call, no `docker login` and no `docker push`. Its only bounds are the 3000 s and 1800 s limits and the write-once `--out-dir`. The ceiling (20 USD) and the approval record apply to `deploy.sh`, which is not part of this section.
- Login in `deploy.sh`, step `ecr-login`, after the apply (the repositories exist only then): `aws ecr get-login-password --region us-east-2 | docker login --username AWS --password-stdin <account>.dkr.ecr.us-east-2.amazonaws.com`. The password is the output of `aws ecr get-login-password` and travels only through the pipe into docker's standard input. No variable holds it, it is not an argument, and the script never prints it. The `docker` wrapper in `lib.sh` gives `login` 120 s and keeps standard input. The account is `SC_ACCOUNT`, from `--account-id`, which is checked against `sts get-caller-identity` and the approval record before the login. This is the path "`docker login --password-stdin` through the wrapper" in the UNVERIFIED list below.
- Where the token does land. `docker login` hands it to Docker's credential store (the macOS Keychain through `docker-credential-osxkeychain`, or an `auth` entry in `~/.docker/config.json` when no helper is configured). That is Docker's own storage, not a file this repository or these commands create, and it is not printed. An ECR token expires after 12 hours.

- Timings. Each `stage_ok` is followed by `STAGE_SECONDS_<NAME>=<seconds>` (for example `STAGE_SECONDS_HADOOP`); the `STAGE[n] name: ok` markers are unchanged. A failed stage records `STAGE_SECONDS_<NAME>=<n> (stage failed)` and `STAGE_SECONDS_TOTAL_AT_FAILURE`. The published record has `STAGE_SECONDS_TOTAL_BEFORE_PUBLISH`; the publish stage's own seconds and `STAGE_SECONDS_TOTAL` print on stdout after the copy, and `PIPELINE_COMPLETE` carries `total_seconds=`, `mr_proof=` and `mr_job_ids_source=`.
- Progress checkpoints. After each finished stage except publish, and right after the Hadoop classification, the script copies `run-record.env`, `progress.env` and the small logs of the reports directory to `reports/runs/<run_id>/progress/` (one `aws s3 cp` per file, `--only-show-errors`, the same key-material scan as the failure path, at most 60 s per checkpoint in all, never aborting, no recursive copy). The prefix holds only the latest checkpoint: the keys are overwritten each time (versioning is off). A step killed from outside (the state machine's task timeout, as in S run 3) does NOT run the exit trap: that was observed in S run 3 (D30), so no `failed/<stamp>/` copy exists after such a kill, and the checkpoints are the only evidence. They leave the evidence up to the last finished stage; what the running stage was doing (its own log) is not in it. The final `publish` of the reports directory does not count `progress/` or `failed/` objects.
- Spark settings (work order 49). `spark-yarn.conf`: `EXECUTOR_INSTANCES=2`, `EXECUTOR_CORES=2`, `EXECUTOR_MEMORY=3g` (was 1, 2, 4g), dynamic allocation still off, applied to CollaborationPipeline, JsonlExport and the capability check alike (one `spark-defaults.conf`). The arithmetic and the limits are in the comments of that file.

On-node time limits (work order 52, Phase 14 D32; written, not run). The limits now are:

`-k 30` sends KILL 30 s after the TERM that the time limit sends, so a command that ignores TERM cannot outlive its limit. A timeout makes `timeout` exit 124, but that status never reaches the report's exit code. Every stage under `timeout` catches the status (`|| rc=$?`) and calls `die`, and `die` always exits 1, so `sc_on_exit` records `FAILED_EXIT_CODE=1` for a timed-out stage, as S run 4 showed (D32). The 124 appears only in the text that `die` writes to stderr, which is the EMR step log: `EVIDENCE: PipelineTool exited 124: ...`, `EVIDENCE: ErBatch exited 124: ...`, or `... (exit 124): ...` for the two Spark applications. It is in no key and no file of the reports directory, so `FAILED_EXIT_CODE` cannot tell a timeout from another failure. (From the GNU coreutils manual, not observed on the node: a command that ignored the TERM and needed the KILL makes `timeout -k` exit 137, so that text would read 137 instead of 124; the recorded `FAILED_EXIT_CODE` stays 1 either way.) A timeout can be told from the stage seconds: `STAGE_SECONDS_<STAGE>=<n> (stage failed)` with n equal to the stage limit (up to 30 s more when the KILL was needed). When the failed-log publish budget is spent, each file not yet uploaded is skipped and named in a `FAILED_LOGS_SKIPPED file=<name> reason=time-budget-spent` line, and a NOTE gives the count; `run-record.env` is uploaded first. The publish stays best effort: it never changes the exit code, keeps the key-material scan, and uses no sync, no `--delete` and no `--sse-c`. The two environment variables are read by the on-node script; nothing sets them in the state machine, so the defaults apply unless a human changes the script or the step. The step cap of the S overlay is 4800 s: Hadoop 1500 + ER 3000 + Spark 3000 + export 3000 would exceed it, so the Terraform step cap, not these limits, is the outer bound of the whole script (the audit with the worst-case sums is in the work order 52 report).

### Execution input contract

Two modes. Any other shape is refused by `run-bounded-pipeline.sh` before it starts anything, and by the state machine's first Choice state.

```
{"mode": "capability-check"}

{"mode": "pipeline",
 "snapshot": "<id of the raw/ prefix: A-Za-z0-9._->",
 "snapshots": "<value of -Dscholarchain.run.snapshots, naming exactly dblp plus the supplied datasets, e.g. dblp=2026-11-05,openalex=2026-11-07,crossref=2026-11-07,orcid=2026-11-07; confirm against the dataset manifest>",
 "run_id": "run-v1-<lower-case canonical UUID>",
 "loader_command": ["scholarchain.some.MainClass", "arg", "..."]}
```

`run_id` shape (work order 46, after S run 2). It must be exactly `run-v1-` followed by a lower-case canonical UUID (8-4-4-4-12 hex), 43 characters, for example `run-v1-3f2b8c1e-5a47-4d0e-9b6a-1c2d3e4f5a6b`. Make one with `printf 'run-v1-%s' "$(uuidgen | tr 'A-Z' 'a-z')"` (macOS `uuidgen` prints upper case, hence the `tr`). Why: it is the path-safe slug of the stable run identifier `run:v1:<uuid>` that core's `StableIds` requires (`RunContext.runSlug` is the identifier with `:` replaced by `-`, and the Hadoop output is `run=<slug>/snapshot=<digest>`). `run-s-pipeline.sh` turns the slug into `run:v1:<uuid>` for `-Dscholarchain.run.id` and keeps the slug for the S3 prefixes, the work directory and the loader argument. S run 2 failed in the Hadoop stage with `Malformed run identifier` because the pinned id was `s-20261114-2`; the scripts then accepted any path-safe id. Now `run-bounded-pipeline.sh` refuses any other `run_id` in pipeline mode, in a real run, a dry run and `--print-digest`, in the input validation, before the approval record is read (message `EVIDENCE: run_id must be exactly run-v1- followed by a lower-case canonical UUID ...`, with the example command and the length of the value it got, never the value, which could be a mistyped key id and the key-material scan has not run yet; a value that fails the older character and length rule keeps `run_id is missing or not valid`). A capability-check input has no `run_id`. The same check runs again on the node, in `validate-arguments`. Cross-check: when the last element of `loader_command` starts with `run-`, it must equal `run_id`, because a different one would make the loader read another run's export (a refusal that does not print the element; a last element that does not start with `run-` is not checked, so the loader command need not carry the id). Changing the script changes `SCRIPT_DIGEST`, so a new approval record is needed. A rerun needs a new id.

`loader_command` goes to the ECS loader task only (its entry point is the storage and rag owners' work). The three scalars reach the node as separate step arguments (never through a shell string) and the scripts validate them again. Reusing a `run_id` is NOT stopped by FileOutputFormat: the Hadoop work directory is `$SC_HOME/run/<run_id>` on the node's local disk and every execution gets a fresh cluster, so the directory never exists and the check in `run-s-pipeline.sh` never fires. A reused id passes the Hadoop, ER and Spark stages and is caught only at the publish stage, by the object-count comparison, after objects under `curated/runs/<run_id>/`, `graph/runs/<run_id>/` and the other run prefixes may already have been overwritten (`aws s3 cp --recursive` overwrites). The only guard is a fresh `run_id` for every execution (the format check proves the shape, not that the id is unused). A cheap pre-start check of the S3 prefix (a list of `curated/runs/<run_id>/`) is a possible later work order, not implemented.

State machine (read from the Terraform, not observed): `ValidateInput` (Choice) -> `CreateCluster` -> `FetchScripts` (copies `bootstrap/` to `/home/hadoop/sc`, fixed 300 s) -> `ChooseStep` -> `CapabilityStep` or `PipelineStep` (one `command-runner.jar bash <script>` step, bounded by `pipeline_emr_step_timeout_seconds`) -> `TerminateCluster` -> `AfterTerminate` -> `RunLoader` (pipeline mode only) or `Done`. The cleanup states, the 900 s terminate and cleanup timeouts and Rule A are unchanged. Steps use `command-runner.jar` (local to the node), not `script-runner.jar` (in the regional EMR bucket, which the `emr_ec2` role cannot read, so it would need an IAM change; the bucket path is from memory, UNVERIFIED). That `command-runner.jar bash <script>` runs as expected, and that the AWS CLI exists on the node, are UNVERIFIED.

### Pipeline mode (the S run, after the capability check passed)

`run-s-pipeline.sh` marks `STAGE[n] name: start|ok|FAIL`: `validate-arguments`, `java`, `fetch-inputs`, `spark-stage`, `hadoop`, `entity-resolution`, `spark`, `export`, `publish`. It records `MAPREDUCE=yarn|local|mixed|unknown` with the current rule (work order 48, human decision D30; the ResourceManager's list decides, the job ids in the log no longer do). `PipelineDriver` runs 1 + datasets + 5 jobs (DBLP extraction, one source-normalization job per dataset, identifier join, blocking, candidate features, team expansion, graph export), so 9 for the three datasets, not 7. The verdict is `yarn` when `yarn application -list -appTypes MAPREDUCE -appStates ALL` lists exactly that expected number (nine) of MAPREDUCE applications and no `job_local...` id is in `hadoop.log`; `MAPREDUCE_PROOF` says `resourcemanager-application-ids`, or `job-ids-in-log` when the log also carried all nine `job_<digits>_<digits>` ids. A `job_local...` id with no YARN job id and no listed application gives `local`; with either kind of YARN evidence it gives `mixed` (mixed is checked before local, local before yarn); anything else (an empty list or another count) gives `unknown`, with the counts in `MAPREDUCE_DETAIL`. No verdict stops the pipeline. The real job ids come from the first source that yields all nine, else from the source with the most ids: the Hadoop log, else `mapred job -list all` and then `mapred job -list` (each under a 60 s timeout, output in `mapreduce-job-list.log`), else ids derived from the application ids (`job_<ts>_<n>` is `application_<ts>_<n>` with the prefix replaced); the source is `MAPREDUCE_JOB_IDS_SOURCE` (`hadoop-log`, `mapred-job-list`, `derived-from-application-ids`, or `none`), and a derived list also gets `MAPREDUCE_JOB_IDS_DERIVATION`. It writes `MAPREDUCE_JOB_IDS`, which `kv` cuts at 400 characters (the file `mapreduce-job-ids.txt` in the reports is the full list, each id with the stage at that position), `MAPREDUCE_JOB_IDS_FILE`, `MAPREDUCE_JOB_COUNT`, `MAPREDUCE_JOBS_YARN`, `MAPREDUCE_JOBS_LOCAL`, `MAPREDUCE_STAGES_EXPECTED`, `MAPREDUCE_STAGE_MAPPING` and `MAPREDUCE_APPS_YARN_LIST` (the count and application ids of the ResourceManager list, which is the proof for `yarn`; full output in `mapreduce-yarn-list.log`). The log names no stage per job id, so the mapping is positional and inferred. `MAPREDUCE_ATTENTION` is `no` for `yarn` and `yes` for anything else; a verdict other than `yarn` also prints a NOTE starting `ATTENTION:` (repeated before the final line), and `PIPELINE_COMPLETE` carries `MAPREDUCE=<verdict>`, the counts, `mr_proof=` and `mr_job_ids_source=`. After the classification a progress checkpoint is published (`sc_publish_progress`). It also records `SPARK_ON_YARN=<mode>:yes`, with `SPARK_APPLICATION=<application id> state=<YARN final state>` and `EXPORT_APPLICATION` for the export (the verdict is now set outside a command substitution, so the id is no longer `none`); it fails the stage when the Spark log shows no YARN application (for example because the application still forces `local[2]`). For the Hadoop output it records `id`, the owner and mode of the output root before and after `chmod -R a+rX`, because the container user for `file:` output on EMR is unknown (UNVERIFIED). `-Dscholarchain.run.id` and `-Dscholarchain.run.snapshots` are always passed (the run id option carries the stable form `run:v1:<uuid>` derived from the `run-v1-<uuid>` slug argument; the slug stays the work directory name, the S3 prefix component and the `RUN_ID=` and final marker value, and `RUN_ID_STABLE=run:v1:<uuid>` is added to the run record; work order 46; only the Hadoop command sets the option, the ER and Spark stages take paths), and so is `-Dio.compression.codecs=` with the Default, Gzip and BZip2 codec classes (work order 44; no LZO, no Snappy). The Spark applications get the same list as `spark.hadoop.io.compression.codecs` in the `spark-defaults.conf` that `write_spark_conf` writes (it was there before work order 44; the list now comes from one constant, `SC_CODECS` in `lib-emr.sh`). It cannot move into `spark-yarn.conf`, whose lines are `KEY=VALUE` with no commas. Work order 45 adds three more `-D` options to the Hadoop command: `-Dmapreduce.map.output.compress.codec=` with `DefaultCodec` (zlib, no native library), `-Dmapreduce.output.fileoutputformat.compress=false` and `-Dfs.permissions.umask-mode=000`. There is no `-Dmapreduce.map.output.compress=false`: every job calls `JobConfig.enableIntermediateCompression`, which sets that key to true unconditionally, so the option would be overwritten; the jobs keep a map-output codec that is already configured, so the codec option is the lever. The jobs write plain text with `TextOutputFormat` through `MultipleOutputs` and never set output compression, so forcing `fileoutputformat.compress=false` only stops a site default from compressing the files the ER and Spark stages read as plain text. Before the hadoop stage the script records `NODE_CONF_IO_COMPRESSION_CODECS`, `NODE_CONF_MAPREDUCE_MAP_OUTPUT_COMPRESS`, `..._COMPRESS_CODEC`, `NODE_CONF_MAPREDUCE_OUTPUT_FILEOUTPUTFORMAT_COMPRESS` and `..._COMPRESS_CODEC` (the node's `core-site.xml` and `mapred-site.xml`, `unset` when absent; `capability-check.sh` records the same in its environment stage, but is not being rerun). The containers, and the output committer in the application master, may run as the `yarn` user, so all data is under `$SC_HOME/run/<id>` and the hadoop stage first records `PERMS_USER` (with umask), the modes of `/home/hadoop`, `$SC_HOME`, `$SC_HOME/run` and the run directory (`PERMS_*_BEFORE` and `_AFTER`), then, each printed as a `NOTE: chmod ...` line: `chmod a+x` on `/home/hadoop` and `$SC_HOME` (traverse only), `chmod -R a+rX` on the raw inputs, and `chmod 1777` (world-writable with the sticky bit, so another user can create its output directories but cannot delete or rename entries this user owns) on the run directory, and later on the Spark and export output directories before those stages. The umask option keeps the directories that tasks create inside them writable for the other user. A chmod that fails is reported, never fatal, and the post-stage `chmod -R a+rX` of each output now also only reports when entries belong to another user. `HADOOP_OUT_FILE_OWNERS_MODES` records which user wrote the Hadoop output files (`user:mode=count`). All of this is UNVERIFIED until a node runs it. The reason for a failed stage (the text after `EVIDENCE:` and in the `die` message) is now, in order: PipelineTool's own `ScholarChain pipeline not started: ...` line, the last line with `Exception`, `Error`, `ERROR` or `FAILED` (the openssl `UnsatisfiedLinkError` is still skipped), or the last three non-empty lines of the log. A line that matches a key-material pattern is replaced by a fixed text. When any stage fails after the reports directory exists, the exit trap writes `FAILED_STAGE` and `FAILED_EXIT_CODE` to a partial `run-record.env`, copies each file of the reports directory (after the same key-material scan; a matching file is skipped with a `FAILED_LOGS_SKIPPED file=<name>` line and its content is not printed) to `reports/runs/<run_id>/failed/<UTC stamp>/` with `aws s3 cp` (no `sync`, no delete), and prints `FAILED_LOGS_PUBLISHED=<s3 uri>`. The whole publish has a shared time budget (default 600 s, `SC_FAILED_PUBLISH_BUDGET_SECONDS`; each call gets the smaller of 300 s and the time left; once spent, the remaining files are skipped and named). An error in that publish is printed and swallowed, so the exit code stays the stage's. A failure in `validate-arguments` happens before the reports directory exists and publishes nothing. A step killed from outside, which is what the state machine's task timeout does, does NOT run the exit trap (observed in S run 3, D30): nothing is published under `failed/` then, and the progress checkpoints under `progress/` are the evidence. Settings are in `scripts/emr/spark-yarn.conf` (memory sizes for an m5.xlarge, `POPULATE_HADOOP_CLASSPATH`, `DEPLOY_MODE`); edit it, upload again, and the next cluster reads it.

Library jars are filtered: `hadoop-*` is excluded from the Hadoop `-libjars`, and `spark-*` and `hadoop-*` from Spark `--jars`, so the cluster's and the distribution's own classes win. The excluded names are recorded (`*_EXCLUDED_LIB_JARS`). Whether `target/job/lib` holds such jars is unknown.
